# 开发指南

## 环境要求

| 项 | 要求 |
|---|---|
| Node.js | ≥ 22（依赖内置 `node:sqlite`） |
| 包管理器 | pnpm ≥ 9 |
| 操作系统 | 不限定（Windows / macOS / Linux 均可） |

## 常用命令

```bash
pnpm install                    # 安装依赖

# 以下是推荐入口：直接调脚本，不经过包管理器
# 合并门禁（必须带分支名，否则第一行的分支提醒不生效）
GIT_BRANCH=$(git branch --show-current) node scripts/check-all.mjs
node test/run.mjs               # 只跑测试

# 各步骤也可以单独跑（在项目根目录）
node node_modules/typescript/bin/tsc --noEmit
node node_modules/eslint/bin/eslint.js .
node node_modules/prettier/bin/prettier.cjs --write "src/**/*.ts" "test/**/*.mjs" "scripts/*.mjs" ".github/**/*.yml"
node scripts/verify-encoder.mjs # 真实模型验证（需联网，不进 CI）
```

（PowerShell 下用 `$env:GIT_BRANCH = (git branch --show-current); node scripts/check-all.mjs`；
完整说明见 [CONTRIBUTING.md](CONTRIBUTING.md) 的「合并门禁」。）

**为什么推荐 `node scripts/...` 而不是 `pnpm run ...`**：某些环境下 `pnpm run` 会因为
pnpm 自身的依赖预检查而失败（报 pnpm 不是命令）。直接调用脚本入口可以绕开这一类不确定性，
而且与 CI 用的是**同一套脚本入口**。

## 导入既有记忆

**仓库里没有迁移脚本，这是刻意的。** 导入不是「照格式搬运」——它要做的是把「别人的结构」映射成 atom：
哪些内容算一条记忆、原子边界在哪，都是语义判决。所以正确形态是**由模型决定、由脚本执行**：
解析来源格式的脚本因来源而异，用完即弃，不进入仓库。

下面是这个流程的设计约束（来源无关）：


| 步 | 做法 |
|---|---|
| ① 导出 | 只读来源，结果缓存成 JSON 便于离线重跑 |
| ② 剥块级元数据 | 文件开头的 frontmatter 那一类元数据块必须剥掉 |
| ③ 切分 | 按 H2 小节切；< 80 字符并入相邻节，> 600 字符按句再切 |
| ④ 编码 | 批量编码后落库 |
| ⑤ 校验 | 逐个原小节标题检查能否在 atom 里找到 —— **脚本自己核，不靠人眼** |

**块级元数据必须剥**：不剥的话每个来源文件的开头那段会自成一个 atom。实测在一次 57 文件的导入里
多出 57 个这样的「原子」——它们彼此高度相似（会拉高相似度分布），且不可能被任何查询召回。

**切分单位选 H2 而不是整卡或段落**：写卡规范本来就要求「一节讲一件事」，边界天然存在；
整卡会让一个 atom 含多个主题（与正交要求冲突），按段落切则太碎（一个论断常跨几段）。

### 导入实测

**首轮（57 个来源文件，2026-10-15）**：

| 指标 | 值 |
|---|---|
| 切出 atom | 279 |
| 落位结果 | 并入 79 / 新建 200 |
| 原小节可定位 | **210 / 210**（导入判据） |
| 写入耗时 | 11.1 ms/条（真实模型） |

**扩容后（442 个来源文件，2026-10-17）**：

| 指标 | 值 |
|---|---|
| 切出 atom | 1374 / topic 955 / entry 21834 |
| 落位结果 | 并入 419 / 新建 955 |
| 原小节可定位 | **604 / 604**（missing 0） |
| 来源维度 | origin 3 类（model / import / user）、scope 5 类 |
| 建库耗时 | 74.2 s（真实模型） |

扩容后的库同时验证了两件事：**定位性随规模不退化**（604/604），以及**上文那条「漏并」机制
不随规模改善** —— 1.44 atom/topic，与首轮的 1.38 几乎一致。所以它不是扩库引入的新问题，
而是同一个阈值问题的稳定表现；处置仍是路线图里的阈值相对化与重标。

**一个必须知道的后果**：导入语料是来源文件的小节（p50 280 字符），同主题对的余弦 p50 只有 0.785、
min 0.642，而阈值 τ_join = 0.78 是拿 30~50 字短句标定的 —— 于是**约一半本该并入的对没并**，
200 个 topic 对 279 个 atom 偏碎。

这不是错并（多成员 topic 的词面重叠都在合理区间，没有把不同话题并到一起），
而是**漏并**：主题偏多、偏细。对召回的影响有限（atom 粒度检索仍工作，实测 6/6 查询有结果），
但主题层会显得零碎。重标阈值或引入相对判据是后续阶段的事，见项目路线图。
## 标准验证库

**验证的前提是「基准库与待测代码同规则」。** 前提不成立时，测出来的差值可能全部来自规则差异，
而不是被验证的那次改动 —— 而且这种差值看起来通常很正常，不会以报错的形式提醒你。

所以基准库自带说明：`meta` 表记录 schema 版本、**入口抽取规则标识**、来源、构建者与时间
（见 `src/db/meta.ts`）。改动任何影响抽取结果的逻辑时，必须同时改 `ENTRY_RULE_ID`
（`src/pipeline/entries.ts`），否则旧库会继续冒充成「同一套规则」。

生成方式固定为一条命令：

```
node scripts/build-baseline.mjs --source <cards.json> --label <名字> [--out .probe/baseline]
```

| 项 | 约定 |
|---|---|
| 来源 | 一个 JSON 数组 `[{path, title, kind, text}]`，正文为 Markdown |
| 产出 | `<out>/lattice.db` 与 `<out>/build-report.json`（自检结果） |
| 自检 | 规则一致 + schema 对象齐全 + 来源的每个小节能被定位到某条 atom |
| 可复现 | 同一份来源、同一顺序、同一规则 → 同一个库 |

**「同一顺序」也是输入的一部分**：入口抽取要读词表（df），而词表随库增长。同一个 atom
在第 1 条写入与在第 200 条写入，得到的入口权重可以不同。

### 基准子集与复跑装置

`verify-recall-baseline.mjs` 回答「这一次改完，召回有没有掉」；`scripts/bench.mjs` 回答
「和改动前那份固定对照比，差了多少，这个差是不是噪声」。两者共用同一份库与查询集，
但后者会额外输出 bootstrap 95% 区间与最小可分辨差 —— 没有这两个数，比例上的小差异
很容易被读成改进（n = 20 时一条命中就是 5 个百分点）。口径、来源与使用限制见
`docs/BENCHMARK.md`。

### 改动前先另存一份快照

基准库会被**按当前规则重建**。所以「改动前后对比」不能用它当「改动前」—— 重建之后，
对照物已经跟着变了，差值恒为 0，而 0 正是最像「没问题」的假象。

正确顺序：**先另存快照，再改规则**。

```
node scripts/snapshot-baseline.mjs [--db .probe/baseline/lattice.db] [--label <名字>]
```

产出 `.probe/snap/<名字>/lattice.db` 与 `snapshot.json`（记录入口规则、规模、sha256）。
标签默认是「库记录的入口规则 + 日期」，例如 `bigram-idf-v4-20261017` —— 它回答的正是
对比时要问的那个问题：这份快照是哪套规则建的。标签已存在时报错，不静默覆盖。

快照用 `VACUUM INTO` 写，而不是复制文件：WAL 模式下主文件可能不含尚未 checkpoint 的事务，
直接复制会得到**没有报错的**残缺副本。

需要「改动前」的 `verify-*` 脚本（`verify-entry-quality.mjs` / `verify-entry-filter.mjs`）
**必须**用 `--before` 指到那份快照；不给就停。`verify-recall-baseline.mjs` 同理，`--db` 必填。
这不是「多打一个参数」，而是把「我忘了指定对照物」从「一切正常」里拆出来：
此前它们各自默认读 `.probe/baseline/lattice.db`，于是重建过的库会**静默地**充当自己的对照。

**`--mock` 只用来验流程**：它用构造向量跑通链路（秒级），向量是假的，召回数字没有意义，
不能当基准。
## 宿主工具

插件只提供工具，**没有 hook**：禁用 LLM 后「轮次结束自动沉淀」必然要调 LLM 做结构化，
与定位冲突。写入与召回都必须是显式动作。

| 工具 | 作用 | 关键点 |
|---|---|---|
| `lattice_write` | 记住一件事 | 内容值得跨会话复用时才调用；`refs` 是显式入口词；`edges` 显式声明关系边 |
| `lattice_recall` | 按需取回 | 返回组装好的三段式文本，不是裸数组 |
| `lattice_expand` | 展开全文 / 列兄弟 | 召回只给了摘要或截断正文时用 |
| `lattice_list` | 列目录 | 「库里有什么」；只读、按写入顺序倒序、**总是分页**（上限 50），可按 kind / origin / scope / topic 过滤 |
| `lattice_feedback` | 反馈上次召回 | `{ kind, ref }`：`ref` 是【锚】段的 1-based 序号；只写独立样本库，不写 edge / 主库、不触发重标 |
| `lattice_ping` | 健康检查 | 报出解析后的数据目录、资源参数、工具清单与样本条数（`samples: { total, positive, negative }`） |

### 工具提示词：只留模型必须知道的

**原则**：「模型管语义，插件管结构」。提示词是模型每轮都看得见的一段文本，写宽的代价不是啰嗦，
是让模型开始按插件的内部结构思考 —— 它会跟着说「atom」「几何定位」，而这些词在它的任务里没有意义。

**判据（每一句都问）**：删掉它，模型还能正确调用这个工具吗？

- 能 → 删。内部机制名、算法名、阈值来历、表名、位定义都属于这一类。
- 不能 → 留，但只留**后果**，不留**机制**。「太短会被拒收」留，「按修复成本分级」删；
  「重复只给提示」留，那层审核叫什么名字与模型无关。

**允许出现的内部信息**（四条都是调用契约，不是实现细节）：

1. **枚举取值** —— kind / origin / scope / mode；
2. **参数的格式与边界** —— id 从哪取、ref 是基于 1 的序号、哪些字段必填；
3. **行为的后果** —— 会被拒收、会被拆成多条、只提示不阻止；
4. **怎么管理记忆** —— 见下一段。这一条最容易在「最小暴露」时被误删。

**第四条：插件有义务说清「怎么正确管记忆」。** 「只留必要的」不等于「能省则省」——
删掉管理方法，模型不会因此更自由，它只会**按自己的猜测管**，而它猜不到这套语义。
必须说清的五件事：

| 管理动作 | 提示词里怎么体现 |
|---|---|
| 什么时候该查 | 答案取决于「之前定过什么」的先查；与历史无关的常识不必查 |
| 什么时候该写 | 值得跨会话复用才写；一次对话里临时说过的不写 |
| **写之前先查重** | 写前先 recall 查一遍；重复只会提示、不会拦，所以查重是调用方的责任 |
| 什么时候该改 | 改口用 `supersedes`；旧条只标记、不删除 |
| 怎么整理 | `list` + `flags` 找出有歧义与未归类的条目 |

**与长度约束的优先级**：长度只能压「同一件事说了两遍」与铺垫，**不能压这四条**。
一个写得短却让模型猜不透的提示词，比一个长但说清楚的更糟。

**必须排除的**：表名（atom / topic / entry / edge）、内部模块名、算法名、阈值常量名与来历、
位掩码定义、「插件配置」这类实现概念。

**长度也是判据**：提示词每轮都进上下文，与内容质量无关地占预算。同一条判据再问一次 ——
**删掉这些字，模型的判断会变吗？** 不会就删。压缩顺序（先动损失最小的）：

1. 与参数描述重复的枚举 —— 工具描述里列过六类，参数描述里又列一遍，删前一处；
2. 例子只留一个，且用最短的那个；
3. 「用于……」「可以……」这类铺垫，直接去掉主语与助词；
4. 解释性从句改成短语（「用户明确说过的」→「用户说的」）；
5. 「不是搜索」「不阻止写入」这类否定只在**防误用**时保留，否则删。

**度量**：每次治理记录「处数 + 总字数」，只允许变少。2026-10-19 一次压缩：**1542 → 995 字（-35%）**，
删掉的全是上面五类，能力相关的一句没动。同轮补回「写前查重」一句（管理方法，见第四条），
净 **1008 字**。当前 **29 处、1008 字**，改动后重新数一遍。
T38（声明关系边）新增 3 处 / 163 字：`edges` 参数及其 `type` / `target` 两个子字段，
内容全是枚举值、参数边界与后果 —— 属于允许的四类，不是治理回退。当时 **32 处、1171 字**。
T26（归档）在 `flags` 的说明里补了「16 = 已归档（默认不列，显式给 flags 时才列）」——
同一处描述，处数不变、净增 29 字。按同一口径推算，当前 **32 处、1200 字**（1171 + 29）。

**回执文本同一条判据**：模型看得见的输出也算提示词。「已写入 atom #N」改成「已写入记忆 #N」——
id 保留（它是后续 expand / feedback 的句柄），结构名去掉。

**现状（2026-10-19，T38 与 T26 后）**：六个业务工具 + 未注册的 `lattice_forget` 规格共 **32 处**提示词、
**1200 字**（口径同上：T26 在 flags 说明里净增 29 字），剩下的内部名词只有四处，都是调用契约 ——
`atom_id` / `edges` / `type` / `target`（参数名，改名会破坏兼容，留到形状变更时统一处理）、
`topic_hint` / `topic`（主题 id）、
`flags`（参数类型是数字，位值无法不暴露；已删掉**没有写入方**的「待拆分」位，并把说明改成语义：
「2 = 两个主题都像、4 = 没有合适的主题」，T26 后又补了「16 = 已归档（默认不列）」）。

**`flags` 为什么不能整个删掉**：它是「找出需要整理的记忆」的唯一入口。删掉之后模型仍然能读写，
但**管不了**——它发现不了哪条歧义、哪条没归入主题。这是「最小暴露」而不是「零暴露」的取舍点。

### parameters 的形状（踩过）

`defineTool` 的 `parameters` 是**「属性名 → 值 schema」的映射**，不是 `{type, properties}`：

```js
parameters: {
  text: { type: "string", description: "...", required: true },
  refs: { type: "array", items: { type: "string" }, description: "..." },
}
```

写成 JSON Schema 包装会在 `defineTool` 调用时抛 `JsonSchemaError` —— 而那是**插件加载路径**，
结果是整个插件加载失败、全部工具都不可用。改参数 schema 后务必跑一次工具测试。

### 低相关的处理（实测教训）

召回**总会**返回 topN 条，不管相关性。曾想设一个硬门槛（低于它就说「没找到」），
但真实模型上一测就否掉了：相关查询的相似度在 **0.45~0.70**，而一条「完全不相关的问题」
拿到 **0.50** —— 在这个尺度上区分不开，硬门槛会把真相关的查询判成没找到。

现行做法是**只标注不拦截**：如实报出最高相似度，弱相关时明示「可能不相关」，把判断权
交回 LLM。阈值 `LOW_RELEVANCE_HINT` 只是提示线，**不是判据**，标定前不要拿它拦截。

## 入口词

入口是「免 token 的检索键」：它不进正文向量，只影响召回能不能找到这条记忆。
**抽取规则改一次，就要同步改 `ENTRY_RULE_ID`**（见上「标准验证库」），否则旧库会继续
冒充成同一套规则。

规则演进中查出来的几件事，推导与证据写在 `src/pipeline/entries.ts` 的注释里，这里只列结论：

| 结论 | 证据 |
|---|---|
| 词表必须从 **atom 正文**统计，不能从 entry 表 | 从 entry 表统计时 df 只有 0~5 六个取值，75.99% 的 atom 十六个权重完全并列，IDF 排序退化成字典序（实际选出「码点最小的 16 个」） |
| 权重并列时的兜底不能是字典序 | 同上 —— 字典序选出来的词没有任何含义；改用「本文出现次数 + 语料频次」后 Recall@12 由 90.0% 升到 95.0% |
| 整段中文（原文切片）必须限制长度 | 切词把连续汉字整段当一个词，「全程没有建分支」这类片段占了展示窗口的 405/2227；限制到四字以内后归零 |
| 单字虚词表**已移除**（v4 规则），但**光删表不够** | 它是人工语言知识，与「插件侧全是几何运算」冲突。实测：只删表不改打分，纯 Entry 路 gold 召回 **65% → 50%** —— IDF 对每个 `df=1` 的候选给同一个最高分，每 atom 约 90 个候选抢 16 个槽位，谁进窗口基本由**码点序**决定；补上 `IDF × log2(1+tf)` 后回到 **70%**。旧表述里那句「挡掉 34%」经实测不符（实际 **61.93%**） |

改这块之前先跑一次 `scripts/verify-recall-baseline.mjs`，改完再跑一次。**召回是唯一能
判定改动好坏的硬判据**，「展示窗口看起来干净了」不是 —— 上面第四条就是被它推翻的。

## 状态信号

注入的锚段每行按需带一个状态标记，回答「这条记忆该不该信」：

| 标记 | 含义 | 字段 |
|---|---|---|
| 无 | 模型写的、未被取代的（大多数） | `atom.origin = model` |
| `·我` | 用户亲口说的 | `atom.origin = user` |
| `·导入` | 从外部资料导入的 | `atom.origin = import` |
| `·已被 #N 取代` | 后来被修订掉了，N 是后继的 atom id | `atom.superseded_by` |

**默认不加标记**：大多数记忆都是「模型写的」，给它们各加两个字只是白占预算，只标需要区分的。

`origin` 默认是 `model` 而不是 `user`，因为判错的代价不对称：模型把用户的话记成 model，
最坏是漏标；反过来把模型的推断标成 user，用户会以为那是自己说过的 —— 而审计正是这个字段
存在的理由。

`atom.id` 自增，**它同时就是写入顺序**；锚段的 `[id]` 已经把这件事变成能看到的事实。

`recall_hits` / `last_recalled_at` 记的是**「被召回并进入了注入」**，不是「模型用了它」——
后者需要反馈信号，而本插件不对模型的心思做假设。这两个字段目前的用途只有「看得出哪些记忆
在被反复取回」，不要把它们读成别的含义。

## 注入预算

注入文本固定三段，各段有配额（`SEGMENT_RATIO`）：**锚 55% / 入口 20% / 路 25%**。

| 段 | 内容 | 剪裁优先级 |
|---|---|---|
| 锚 | 记忆正文（信息本体） | **最后才动**，且保底 3 条 |
| 入口 | 命中主题的入口词 | 中间 |
| 路 | 一跳关联的摘要行 | **最先砍** |

超预算时按 `TRIM_ORDER` 依次降级：路砍到 5 行 → 入口砍到每主题 4 条 → 锚降级为摘要
→ 路清零 → 锚减到保底。**顺序是行为契约**：测试直接断言「触发的裁剪必须是该数组的前缀」，
所以往中间插一步会立刻被测试挡下。

配额是**上限而非目标**：库里的内容总量不足时，锚段占比低于 55% 是正常现象
（没有足够的信息可放）。反过来，若锚段长期显著低于 55%，通常意味着入口段在膨胀 ——
检查 `entryLineMaxChars` 与每主题入口条数。
### 注入档位

注入规模不只由预算决定，还由**这次的匹配质量**决定 —— 无关查询比相关查询更贵是荒谬的。

| 档 | 触发（top1 余弦） | 锚 | 入口 | 路 |
|---|---|---|---|---|
| 完整 | ≥ 0.55 | 不限（由预算裁） | 完整 | 有 |
| 精简 | 0.45 ~ 0.55 | ≤ 8 条 | 完整 | 无 |
| 摘录 | < 0.45 | ≤ 3 条且降级为摘要 | 每主题 4 条 | 无 |

实测依据（279 条基准库）：相关 gold 20 条 top1 min 0.524 / p50 0.683；无关 4 条 max 0.398。
**两者之间是空的**，所以阈值本身不敏感，取空隙中间是为了容错而不是拟合。
效果：无关查询的注入字符从约 4968 降到 **995~1056**，同时 gold 的 Recall@12 保持 95.0%。

**档位只改初值**：超预算时仍然按 `TRIM_ORDER` 依次降级，「锚不为其他段让路」那条行为
契约不因分档而改变，只是起点不同。

**纯词面模式（无查询向量）不降档**：没有余弦可依时宁可多给几条 —— 降档是真的丢信息，
多给只是多花一点预算。

## 与机器相关的参数

有一类参数写死会出事：它们的合理取值取决于**机器内存与磁盘**，不是代码逻辑。
这类参数集中在 `src/util/memory.ts` 里推导，规则与依据都写在那个文件中。

| 参数 | 推导 | 为什么不能写死 |
|---|---|---|
| `mmap_size` | clamp(库大小 × 1.5, 64 MB, min(256 MB, 内存 ÷ 8)) | 小库不需要大窗口；小内存机器给大窗口会白占物理内存 |
| `cache_size` | clamp(内存 × 5%, 16 MB, 128 MB) | 内存越大缓存越有用，但收益会饱和 |
| `busy_timeout` | max(5 s, 单条写入耗时 × 200) | 慢盘上 5 秒可能不够，直接抛 SQLITE_BUSY |

三者都可以在插件配置里显式覆盖（`mmapSize` / `cacheSize` / `busyTimeout`，单位字节与毫秒，
留 0 表示自动）。`lattice_ping` 会报出**实际使用的值**，不必读代码去猜。

**加新参数时的约定**：先问它随什么变化。随模型变的写进模型配置，随语料变的留给标定脚本，
只有随机器变的才放到这一层 —— 放错了会得到一个在别的机器上不对、而且没人知道为什么不对的数字。

## 模块划分

```
src/
  index.ts        插件入口：契约导出、**配置 schema 与默认值**、生命周期、只读路由
  db/             存储层：schema、连接与迁移、仓储、检索
  encoder/        向量编码：模型加载、批处理、可用性探测与降级
  pipeline/       业务管线：写入、召回、注入组装、维护
  tools/          暴露给宿主的工具
  log/            降级日志：独立数据库、事件白名单、缓冲、轮换清理、导出与清空
  samples/        校准样本：独立数据库、会话级「最近一次召回」、自动收集与淘汰规则
  util/           纯函数工具：文本、向量、聚类、日志
```

**依赖方向（强制）**：`tools → pipeline → {db, encoder} → util`。

反向依赖一律禁止。此外，`db` / `encoder` / `pipeline` 必须是**不依赖宿主 API 的
纯 Node 模块**——这样它们可以脱离宿主独立测试，也保证将来替换宿主接口时改动收敛在
`index.ts` 与 `tools/` 两处。

`samples/` 与 `log/` 同形：旁路数据，只依赖 Node 内置模块（外加 `util/` 的向量编码与
资源推导），并向 `log/` 借一个 `logEvent` 记写失败；它对 `pipeline/` 只 import 一个
**类型**（`RecallMeta`，编译后不存在），不在运行时反向依赖业务管线。它对外暴露
「记一条样本 / 报条数 / 记最近一次召回」三件事，写入一律先在内存排队。

`log/` 是叶子模块：只依赖 Node 内置模块（外加 `util/` 的资源推导），不反向依赖
`pipeline` / `tools`。它对外只暴露一个写入口 `logEvent`（入队即返回）；召回路径上
不允许出现日志库的同步 IO。**除 `log/` 外，源码里出现日志库文件名或 `INSERT INTO log`
会被门禁判红**（`scripts/check-log-boundary.mjs`）。

## 关键约束

工程的硬约束见 [PRINCIPLES.md](PRINCIPLES.md)（职责边界与行为边界）。下面是同样有具体失败模式的实现约束：

1. **向量常驻内存**：召回路径不要通过 SQL 逐条读向量。
2. **召回是只读快路径**：查询日志、入口反哺等全部异步，不得阻塞返回。
3. **热路径零分配**：复用缓冲区，不在循环里创建对象或闭包。
4. **两两比较先分桶**：任何 O(N²) 操作都必须先分桶，否则规模一上来就不可用。
5. **长任务不进请求路径**，且执行期间分片让出事件循环。
6. **写入事务固定行数**：长任务走"只读导出 → 内存计算 → 短事务切换"的影子重建。
7. **模型懒加载**：插件激活时只注册，不做重活，避免拖慢宿主启动。

## 测试

- 纯函数 → 单元测试，覆盖边界（空输入、超长、非对齐数据…）
- 涉及数据库 → 用内存库或临时文件，测完清理，临时文件加入 `.gitignore`
- 涉及外部模型 → 必须能在模型不可用时降级通过

**每个用例都必须显式给它自己的临时库目录。** 不许留空、不许用 `homedir()` 或
`DSH_HOME` 拼路径：`dataDir` 为空串时 `resolveDataDir` 会回落到用户的**真实库**
（`~/.dsh/lattice`），而任何会打开库的用例（`ping`、体检路由、工具的 `execute`）都会
读写它。两个后果都已经发生过：宿主进程正持有时以 `SQLITE_CANTOPEN` 失败（整套门禁挂在
与被测行为无关的事情上），以及用例在用户的真实记忆库里留下写入。

约定写法：`mkdtempSync(join(tmpdir(), 'dsh-lattice-<用途>-'))`，`afterEach` 里先
`closeRuntime()` 复位全局单例再删目录，钩子写在 `describe` **内部**（顶层钩子在 node:test 里
是全局的，会串到别的文件）。

这条由 `test/isolation.test.mjs` 自动检查：扫全部 `*.test.mjs` 的字面量，出现空串、
`homedir()` 或 `process.env.DSH_HOME` 直接红。

单元测试**注入向量**而不加载真实模型：判据是阈值，只有注入向量才能构造出"刚好
0.77"这类边界样本，真实模型反而测不了边界。真实模型的表现交给 `scripts/` 下的
验证脚本（它们会下载模型、写临时库，因此不进 `test/`，也不进 CI）：

| 脚本 | 验什么 |
|---|---|
| `scripts/verify-encoder.mjs` | 模型可用性：维度、归一化、同义改写的相似度是否高于跨域 |
| `scripts/probe-threshold.mjs` | 落位阈值的可分性：同主题对与跨主题对的余弦/词面分布 |
| `scripts/verify-write.mjs` | 写入闭环：同义改写能并入、异质记忆不被误并 |
| `scripts/verify-recall.mjs` | 召回闭环：已知查询能否命中它该命中的那条记忆 |
| `scripts/verify-view.mjs` | 注入组装：各段实际字符占比与裁剪是否按顺序触发 |
| `scripts/verify-tools.mjs` | 工具端到端：注册、写入、召回、展开、健康检查（真实模型） |
| `scripts/verify-scope-write.mjs` | scope 端到端：真实编码器写入不同 scope、再按 scope 召回，验隔离（6 项判据） |
| `scripts/verify-entry-quality.mjs` | 入口词质量：`--before` 快照 vs 按当前代码重建入口，比噪声与 Recall |
| `scripts/verify-entry-filter.mjs` | 入口过滤的净效应：只剔除噪声词、不重排，看 Recall 是否下降（`--before` 必填） |
| `scripts/verify-recall-baseline.mjs` | 召回回归：指定库上的 Recall@12 / @24 与平均注入字符（`--db` 必填） |
| `scripts/verify-disk-write.mjs` | 落盘写法：证明模板字符串承载会失败、单引号数组 + join 不会 |
| `scripts/snapshot-baseline.mjs` | 另存对照库快照到 `.probe/snap/<标签>/`（改规则**之前**跑） |
| `scripts/build-baseline.mjs` | 重建基准库（`--source <cards.json>`），自带三条自检 |
| `scripts/print-thresholds.mjs` | 阈值登记表：打印名称/值/标定场景/可变条件 + 与设计文档对照 + 库规模告警 + 覆盖核对（不需模型，可随时跑） |

基准库由 `scripts/build-baseline.mjs` 生成、快照由 `scripts/snapshot-baseline.mjs` 另存
（见上「标准验证库」）。**改入口规则类的验证脚本不再自带默认库路径**：要对比就显式给
`--before <快照>`（或 `--db <库>`），缺了参数会停下来并说清怎么补 —— 默认值在这里等于
把「没有对照组」显示成「差值 0」。

调整落位阈值时，先跑 `probe-threshold.mjs` 拿到分布，再改 `DEFAULT_THRESHOLDS`，
并把新的数字写进那段注释——**阈值必须带着它的标定依据一起存在**，否则下一个人
无从判断它是怎么来的、能不能动。

**阈值登记表**（`src/thresholds.ts`）是这条约束的载体：每个经验取值在那里有一行，
写明标定场景（哪个库、多少条、什么来源分布）与可变条件，并引用源码里的真值而不是
复制一份数字。`print-thresholds.mjs` 负责打印、核对覆盖（源码里的数值常量若既没登记
也没进豁免清单，命令以非零码退出）与规模告警（当前库越出某行的标定场景时显式报出）。
新增或改动阈值时，**先跑它**看缺口。

**档位阈值按库规模重标**（`src/pipeline/calibrate.ts`）。`view.ts` 的 `tierOf(topCosine, briefMin)`
第二个参数默认仍是旧值，而运行时经 `briefMinFor(db)` 取标定值 —— 它按库的 atom 数从一张**实测锚点表**
插值（12 → 0.466 … 1374 → 0.525，log2 尺度、两端夹紧）。库小于 12 条退回默认值、大于 1374 条
夹紧不外推。取值是库规模的纯函数，每次一次 `COUNT(*)` 加几次比较，无缓存。

之所以是「重标」而不是「改相对判据」：相对判据那条路**实测不通**（四个绝对候选全不合格），
而逐点最优的绝对阈值只从 **0.492 漂到 0.525** —— 库大了 115 倍只漂 6.7%。**所以形式不变、值随规模走。**

**锚点表是标定结果，改它等于改档位行为** —— 要改先看 `calibrate.ts` 里每个锚点的 `evidence`
与那次实测的报告。另：真机库当前规模（十几条）**远低于阈值稳定所需的 192 条**，所以那里的值是插值、
不是标定值，工具层的提示线也还没跟上（那条分叉记在 T23-b 的未确定项里）。
