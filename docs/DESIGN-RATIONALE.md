# 为什么这么定：六处结构决策的来历

`docs/ARCHITECTURE.md` 讲「现在是什么」。这份文档讲「为什么是它，以及当时否掉了什么」。

两者不能互相替代：前者能由代码核对，后者不能 —— 一条被否掉的路在代码里不会留下痕迹。
所以下面每一条都写清四件事：起点的问题、定了什么、否掉了哪几条以及为什么、代价是什么。

六处决策的共同点是**都改过对外语义**，不是内部实现细节：同一条记忆会不会出现在召回里、
一条线由谁算、读操作能不能写库、库的结构由谁声明、两个入口写同一件事算不算错、
插件要不要拿运行期的判断去改自己的行为。

文中的行号与数字都是写作时（提交 `44c2f80`）的值，代码改动后以函数名为准。

## 一、取代在召回里生效，而不是只做标记

**起点**：写入接口有两个入口都能表达「这条取代了那条」—— 顶层参数 `supersedes` 写
`atom.superseded_by` 列，`edges` 里的 `supersedes` 类型写 `edge` 表。两者互不相通。

**实测推翻了问题本身**：一个真实使用的库（366 条 atom）里，`superseded_by` 非空 24 条，
`edges` 里的 supersedes / duplicate 边 0 条。列里早就有数据，缺的不是写入，是**读** ——
`superseded_by` 只在显示处与重聚类取样时被读，召回路径只是把它 SELECT 出来、不过滤。
所以「要不要把两个入口打通」是伪问题：把 `edges` 的 supersedes 也写进列，召回结果一条都不会变。

**决定**：召回路径加一道取代压制（`src/pipeline/search.ts` 第 695 行的 `suppressSuperseded`）。
规则分两步，因为一步做不到：

1. 截断前：候选里一条记忆的取代者也在候选里 → 压掉旧条；
2. 截断后：取完 topN 再核 —— 取代者不在最终结果里就把旧条放回，并在注入文本里写一句
   「另有 N 条已被取代，未列出」。

**为什么必须两步**：第一版按「取代者在候选集里」判，实测压掉 86% 的条目，包括替代品
根本没进结果的。原因是向量路默认返回 kVec 条，库小的时候几乎全进候选。判据只有落在
最终结果上才有意义，而最终结果在截断之后才确定。

**结果**（同一个库的副本，24 条被取代）：压掉 18 条，其中 16 条的替代品在最终结果里；
另外 3 条原文是表格碎片，改前也召不到。补充一组构造数据（49 对「旧知识 → 新知识」、
98 条记忆的库）：旧条在注入文本里的出现率 49/49 → 1/49；用户拿旧陈述本身当查询时，
新条排第一 0/48 → 39/48。

**代价**：注入字符中位从 4621 涨到 4916（+6.4%），花在「被放回的旧条」上。这是有意的 ——
取代者不在结果里时，旧条是唯一能回答提问的东西，只是要标清它过时了。

**否掉的方案**：

- 只补工具描述，让写的人知道两个入口效果不同 —— 这是止血不是修复，那 24 条照常参与召回。
- 按候选集判 —— 见上，压掉 86%。
- 保留 `edges` 的 supersedes 并把提示写强 —— 见第五节。

**配套的撤销入口**：压制让「写错一次」变成「这条记忆从召回里消失」，而当时没有任何一步能
撤销。所以同一版加了 `lattice_write` 的 `unsupersede` 参数（`src/tools/index.ts` 第 199 行）：
`supersedes` 建立标记、`unsupersede` 清掉标记，两者不能同时给。没有并进上一次改动，
是因为两件事的失败方式不同 —— 混在一起会让「撤销路径是否完整」被「旧条会不会出现」的
测试盖住。

## 二、「有没有内容」的判定线按库自算

**起点**：旧方案发布一张全局的绝对阈值表，并按固定值把相关性分三档。两个问题：
分档用的是绝对值，跨库不成立；表是外部包标定出来的，用户手里的库一变，表就过期。

**实测**：无关查询的 top1 余弦中位数在三个语料库上是 0.420 / 0.482 / 0.403（每库 24 条
无关查询），极差 0.079 —— 三个库规模接近（1374 / 1346 / 1496 条 atom），同一张线
在新闻上过严、在 Vue 上过宽。

**决定**：线由本库自己算 —— 取一组与用户内容无关的中文问句（48 条，随代码发布，
见 `src/pipeline/refdist.ts` 第 28 行 `REFERENCE_QUESTIONS`），在用户库上各取一次
top1 余弦，取 90 分位（`REFERENCE_QUANTILE`，同文件第 80 行）。线是分布的统计量，
不是某个语料上量出来的常数。

**为什么用分布而不是标签**：判断「这条相关吗」需要人标注，而标注拿不到；判断「无关提问
在本库能得多少分」只要分布。这是目标换了，不是工程偏好 —— 换成分布之后，
「用真实反馈重新标定」整条链不需要了（第六节）。

**否掉的三种「造一个与库无关的东西」**（都实测过）：

- 随机向量当对照：p90 只有 0.13，而真实无关查询是 0.42–0.54 —— 线压得太低，判据永远说「有内容」。
- 用本库内容拼接成伪查询：p90 到 0.88–0.90，比相关查询的 p10 还高 —— 两段都来自本库，
  编码后落在库语义空间的中心附近，「语义不连贯」不等于「与库无关」。
- 用库外语料：只在新闻上成立（+0.010），技术笔记 +0.226、Vue +0.214 —— 三个库互为近亲，
  不存在真正的库外。

**条数从 24 改成 48**：原来用「同一批 24 条里重抽样」证明够用，那个判据测的是估计误差，
不是泛化。改用交叉验证（一个库建的线判另一个库的 24 条）后，24 条时越线率在 0%–25% 之间摆，
48 条合并后是 10.4%，正合「取 90 分位」的意图。

**失效线 0.65**（同文件第 99 行）：库的内容面比内置问句宽太多时，线会被抬高到判不出内容。
它要读成「只有引入一个比现有语料更宽的来源（百科、全网新闻）才会显著上升」，不是
「atom 越多越危险」—— 三库合并 4216 条 atom 后 p90 仍只有 0.540 / 0.585，与最宽的单库同值。

**代价**：判空率从 0%（旧实现给 24 条无关查询一律装 3 条、767–844 字符）变成 83%–100%。
这是这次改动里用户唯一能直接感觉到的变化，所以判空的每一种原因都要用固定句子说清
（判没内容 / 库还小判据不稳 / 候选耗尽 / 只选出一条 / 预算不够 / 线自己失效），
不静默、不混成一句。

## 三、三层分工与「读只追加第三层」

**起点**：把库里的东西分成「真相 + 其余」两层不够用 —— 有些数据不是算出来的，但读操作
会往里加（命中次数、最近一次被召回的时间），它也丢了没法恢复。

**决定**：分三层，依据是「谁改它、丢了能不能恢复」。

| 层 | 内容 | 权限 |
|---|---|---|
| 真相 | `atom` 的正文与各语义列、`edge` 里调用方声明的行、调用方显式给的入口词、墓碑、拆分队列 | 只能由写操作改，丢了无法恢复 |
| 可重算派生 | `topic` / `atom_topic` / `atom.topic_id`、推断边、`atom_pair` | 可以由写路径或显式维护命令重建，**不许由读触发** |
| 只能累积的事实 | 命中次数与最近召回时间、`learned` 入口的计数与权重 | 读可以追加 |

一条话的原则：**读只能追加第三层，不能改第一层，也不能重建第二层。**

**为什么这条原则值得为它付代价**：读路径原先会在召回时补建推断边，判据是「表里有没有
推断边」。实测另一个真实使用的库（373 条 atom，稍晚的一份）只有 68 条推断边（全量重建能建 1412 条、耗时 61 毫秒），
按那个判据 68 条已经算「建好」—— 于是 91.4% 的 atom 在图路上出度为 0，四路召回退化成三路，
而系统认为自己完整。三处错位叠在一起：

1. 触发器：几何数据的产生条件是向量变了，与「有人来查询」没有因果关系；把重建成本摊到
   第一次召回，是成本最贵的位置。
2. 判据：「有边就算新鲜」问的是「有没有」，不是「够不够」；应该数「图路出度为 0 的 atom 数」。
3. 契约：读路径建边让只读连接拿不到完整结果，与「只读连接召回与可写连接逐字符一致」直接冲突。

**现在的分工**：写入路径给新原子局部补边（`src/graph/infer.ts` 第 455 行 `linkNewAtom`，
实测写入后 7 毫秒内到位、8 条双向边）；存量库与导入库跑 `scripts/rebuild-graph.mjs` 全量重建；
召回只报数（「声明边 N 条，推断边 M 条」），不写库。

**代价**：有 atom 但推断边偏少的库，升级后不会自愈，要手动跑一次命令。让它成立的原因，
是这条原则比替用户省一条命令更重要。重建后这个库出度为 0 的 atom 从 341 条（91.4%）
降到 7 条（1.9%）。

**一个边界情形**：`embedding` 与 `extracted` 入口词都能从正文算出来，但**没有重建命令** ——
换编码器只能全库重写。它们属于「可重算，实践上不可重算」，判据里单独标注，不并进第二层。

## 四、状态各占一张专用表，版本链只留一步快照

**起点**：库的元数据放在一张 key-value 表里（`key` / `value` / `updated_at`）。它有两个毛病：
格式只写在注释里；同一件事的几个字段可以分开写，写到一半失败就留下半套状态。

**活证据**：这张表里存了一个 `schema_version`，「方便只读打开时也能读到」。在一个真实使用的库里它写着 3，
而 `PRAGMA user_version` 已经是 4 —— 没有任何机制会同步这两份，副本必然漂。

**为什么不能就地整理**：有三条约束挡着 —— 不许升 `user_version`、要向上兼容旧库、
要向下兼容旧插件。逐条放宽之后结论才变：

| 放宽 | 解锁的东西 |
|---|---|
| 允许升 `user_version` | 可以改结构（加表、删表） |
| 首次发布前不考虑前向兼容 | 旧插件打不开新库可以接受 |
| 迁移只在本机做，发布版只留一份快照 | 不用写历史增量链，新建库不再重放历史 |

**决定**：

- 状态各占一张单行表：`build_info`（谁在什么条件下建的库）、`recluster_state`（整理进度）、
  `split_queue`（待拆分的长文段落）。前两张用 `id = 1` 的主键约束保证只有一行，字段一起写；
  第三张有外键指向 `atom`，删记忆时跟着消失。
- `SCHEMA_VERSION = 5`，`MIGRATIONS` 只有一份完整快照（`src/db/schema.ts` 第 338 行），
  打开时 `from` 不在 {0, 5} 里就直接报「该版本来自未发布的内部构建」。
- 打开时比对结构（`src/db/open.ts` 第 135 行的 `migrate` 与它后面的 `assertSchema`）：
  用 `listObjects` 列出库里真实存在的对象，与建表语句里声明的对象集比对，不符就报错并列出差异。

**否掉的方案**：

- key-value 表就地整理（加类型列、键名前缀、状态机合并）：解决不了「状态机部分写」与
  「清单整份读-改-写」，而放宽前向兼容之后，换成专用表的成本已经降到「建几张表、搬几十字节」。
- 一张 state 表加 JSON 值：回到「格式靠约定」，而且整份读-改-写，并发会互相覆盖。
- 一张 state 表加 `ANY` 类型列，或纯 STRICT 表：类型保住了，但状态机仍是多键、仍会部分写；
  STRICT 只约束存储类，不解决语义问题。
- 状态外置成 JSON 文件：复制库要连文件一起带、只读打开读不到状态、状态与数据没法同事务。
- 快照 + 保留历史增量链：首次公开发布，外部没有历史版本的库，保留没有服务对象。
- 继续重放历史语句（35 条、耗时 6 毫秒）：6 毫秒不是问题，问题是第一版建表语句会被永久冻结 ——
  后来的列不能合并回去，否则中间版本的 `ALTER` 会撞重复列。

**后来删掉了两张表**：原计划给一个独立的标定工具保留一张 key-value 表写校准快照 ——
该工具拿真实写入样本算判定阈值，与本插件分开发布、不在本仓库里。标定路线退役、工具归档之后
（它的存储约定是「表必须先存在，它只往里加键」），这张表和另一张空的标定状态表一起删了。
后果写在 `CHANGELOG.md`：将来要恢复标定，得先改标定包的存储、再单独加表 ——
跨包契约不能由本仓库单方面恢复。

**代价**：首次发布之后仍要重新累积增量链。一旦有外部库在外面，「只发快照」就不成立了，
那时起每次结构变更都要加一步迁移并保证旧库能一路升上来。

## 五、去掉 `edges` 里的 supersedes

**起点**：两个入口写同一件事，一个生效、一个不生效。在第一节之后，这个不一致开始伤害用户：
用 `supersedes` 写的取代会让旧条退出召回，写进 `edges` 的同样语义什么也不做。

**实测**：一个真实使用的库的 `edges` 表里 supersedes 边 0 条 —— 去掉入口没有兼容成本。

**决定**：写入时拒掉这个类型并把调用方指回顶层参数（`src/pipeline/write.ts` 第 883 行）。
理由：同一个语义两个入口，一个生效一个不生效，正是当初要解决的问题；去掉入口比反复解释便宜。

**否掉的方案**：保留它，只把工具描述里的提示写强。提示再强也只是提示，用户不会读两遍参数表。

## 六、关掉运行期的样本反馈

**起点**：设计里有一条「越用越准」的链：用户对召回结果给出有用 / 无关的判断 → 存进样本库 →
四道闸判断样本够不够 → 重新标定 → 改判定线。

**实测**：这条链在真实使用中没有发生过。跑了几天之后样本库只有 1 条（用户手动给的），
自动收集的负样本 0 条；入口层的学习路径同样推不动 —— 1870 条学习来的入口词权重全部停在
0.3，命中次数最大 2（1747 条只被反哺过一次），而升档门槛是 0.6。

**决定**：不是「关掉一个功能」，是**目标被替换了**（第二节）：判定线改成算分布之后，
标签不再是输入。于是样本库、四道闸、重标那一条链一起删除（源码 871 行、测试 566 行），
`lattice_feedback` 的定义保留在 `src/tools/index.ts` 第 679 行但**不进工具表** ——
保留它，是为了把「这里曾经有过它、为什么」固定在代码里，而不是靠 git 历史。

**三条否决理由**（都在删除前核实过）：

1. 升档门槛实测不可达：权重恒 0.3，而门槛 0.6，接一次反馈推不过去。
2. 阈值不再收运行期证据：判定线只吃分布，标签接进来也没有落点。
3. 复用物不在代码里：「最近一次召回」是会话内存快照，要接入口层得另造一条「反馈 → 入口」
   的映射，等于把刚删掉的样本链再造一半。

**代价**：插件从此不会知道召回好不好。判定线只保证「与库无关的问题不命中」，
不保证「相关问题必命中」。如果将来「越用越准」重新成为核心，要重新论证两件事：判断无偏、
样本充分 —— 这两条本次都没有证据。

**留下的三条接口纪律**（与样本无关，写进了 `docs/INTEGRATION.md`）：判断类工具只收语义序号，
不收结构 id（一个只记录判断的工具不该携带能解释成「对某条记忆动手」的句柄）；
引用「上一次调用结果」的参数，快照生命周期必须等于会话；写是调用目的时必须在回执里说清成败，
写是副作用时可以静默但必须写明失败方向。

## 附：四条可复用的判断

1. **门禁全绿不等于功能可用**。一条检查如果不经过「用户实际会敲的那条命令」，
   它就证明不了那条命令能跑。本例：门禁跑查询函数，测试直接调函数，而三条命令的分派路径
   没人覆盖 —— 命令全崩、门禁全绿、当时的全部测试（456 条）全过。
2. **集合语义变了，默认参数必须跟着变**。一个集合从「全集」变成「例外清单」之后，
   `entries = 全集` 这类默认值会让调用方静默漏掉搬走的那部分（本例 117 条），
   而表现是清单变短，看起来像缺口都补完了。
3. **冗余副本必然漂**。要存两份的，先问「谁来同步」；答不上来就删掉一份。
4. **版本号是声明，结构断言是证据**。手工改库、迁移漏一条索引、有人直接把版本号改成最新 ——
   这三种情况下版本号都对、结构都不对。所以要再加一道打开时的结构比对。
