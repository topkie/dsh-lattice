# 基准：召回子集与复跑装置

> 本文说清三件事：这个基准**测什么**、**怎么复跑**、**哪些话不能拿它说**。
> 首版之后每一次会改召回行为的改动，其「不退化」都以这里的结果为对照。

相关文件：

- `scripts/bench.mjs`：一条命令跑完的装置，只接受本地路径，自身不联网；
- `bench/fixtures/queries.example.json`：查询集格式的示例（**假查询**，真实查询集不入库）；
- `bench/results/`：每次基线一份 JSON，文件名是被测提交号；
- `.probe/baseline/lattice.db`：本机基准库（**不进版本控制**，见 `.gitignore`）。

## 一、怎么跑

```bash
# 0. 先有 dist（脚本 import 的是编译产物，不是源码）
node node_modules/typescript/bin/tsc -p tsconfig.json

# 1. 分开给两个路径
node scripts/bench.mjs --db <lattice.db> --queries <查询集.json> --out <结果.json> --sha <提交号>

# 或 2. 给一个目录，里面放 lattice.db 与 queries.json
node scripts/bench.mjs --data <目录> --out <结果.json>
```

可选参数：`--bootstrap <次数>`（默认 10000）、`--seed <整数>`（默认 20261018）、`--sha <提交号>`。

**为什么不给默认库路径**：本项目的基准库不是固定路径，而是「这次要跟哪一份比」的问题。
默认值会把「我忘了指定」变成「一切正常」，同一理由见 `scripts/lib/compare-db.mjs`。

### 环境准备

- **编码器模型**：固定 `Xenova/bge-small-zh-v1.5`，与 `scripts/verify-recall-baseline.mjs` 同一个；
  模型文件需已在本地缓存。脚本不下载、不重试、不换模型。
- **没有编码器就直接失败**（退出码 2）。不降级跑：降级时 recall 会退回纯词面、指标静默掉一大截，
  跑出来的数字最像「这次改动变差了」—— 那是装置坏了，不是被测对象坏了。
- **查询集与库都自备**：仓库里没有语料，也不提供获取脚本（见第五节）。

## 二、口径

### 2.1 指标定义

| 字段 | 含义 |
|---|---|
| `set` | 查询集名字（取查询集文件的 `name`，没有就用文件名） |
| `n` | **有 target 的查询条数**，recall 的分母就是它 |
| `nTotal` | 查询集总条数（含没有 target 的） |
| `recall@5` / `recall@12` | 前 5 名 / 前 12 名里出现「target 对应的任一 atom」的查询占比 |
| `hits5` / `hits12` | 上面比例对应的命中条数（整数，便于核对） |
| `p50_ms` / `p95_ms` | 每次 `recall()` 调用耗时的中位数与 95 分位，**不含编码** |
| `atoms` / `superseded` | 库里的 atom 总数、其中 `superseded_by` 非空的条数 |
| `ci95` | 两个 k 的 bootstrap 95% 区间 |
| `minResolvable` | 最小可分辨差 = 1/n |
| `querySet` | 查询集文件的 sha256、条数、有 target 的条数 |
| `topN` / `model` / `bootstrap` | 装置参数，写进结果便于核对「比的是不是同一个装置」 |

三条容易读错的口径，都在代码注释里重复了一遍：

1. **recall 的分母只是有 target 的查询**。没有 target 的查询只参与耗时统计。
   把它们算成「未命中」会把 recall 拉低到没有意义的数 —— 那是另一种假的准确。
2. **目标判定用来源**：`target` 与 `atom.source_ref` 相等即算命中。这测的是「这条来源切出来的
   atom 有没有进前 k」，不是「这条 atom 有没有用」。
3. **耗时只包住 `recall()`**。编码是一次性成本、也可被调用方复用；混进来会把「检索变慢」
   与「模型变慢」搅成一个数。

召回条数取 24（`topN`），与生产默认一致；Recall@12 就是从这个 24 条列表的前 12 名里取。
为什么不直接召回 12 条：24 条是运行时真实交给注入层的规模，测它才测得住生产路径。

### 2.2 子集怎么切，为什么不是全量

**子集不是抽样，是固定样本**：一份查询集 + 一份库，一起固定下来，之后只准换被测代码。
查询集的身份由 sha256 记录，两次跑不只比数字，也比 sha256 —— sha256 变了就不是同一份子集。

为什么不做全量：

- 指标是比例，全量的收益只在「把 1/n 压小」这一项上；而每加一条查询都要人工写 target，
  成本在标注不在算力。把 n 从 20 加到 200，最小可分辨差从 5 个百分点降到 0.5 个百分点，
  这是唯一值得投入的方向（见 2.4）。
- 公开集是长会话、长文档；本插件面向短卡片。全量不会让对照更可信，只会让「切卡口径」
  多一层不确定（见第五节）。
- 本仓库不做语料获取：没有下载器，也就没有「一键全量」。全量由复现者自己持有。

### 2.3 bootstrap 区间怎么算

- **重采样单位是查询**，不是命中。一次重采样里同一条查询可能被抽中两次、另一条一次不中，
  这样才把「换一批同样大小的查询，recall 会飘多少」表达出来。
- B = 10000，种子固定 20261018（写死，可用 `--seed` 覆盖）。同一种子给同一条重采样序列，
  区间才可复现 —— 这是判据 1「逐字节一致」覆盖到区间的必要条件。
- 取 2.5% 与 97.5% 的**最近秩**分位数，不插值；输出保留 4 位小数。
- 不用正态近似：比例接近 0 或 1 时正态区间会越界（出现负数或超过 1），百分位法不会。

区间说明的是「这一小批查询上的不确定性」。**两个数字的区间重叠时，不能认为它们有差别**；
区间不重叠只说明「在同样大小的另一批查询上也大概率不同」，仍不等于改进。

### 2.4 最小可分辨差

**最小可分辨差 = 1/n**，就是一条命中在比例上的重量。

| n | 1 条命中的重量 |
|---|---|
| 20（当前内部集） | 5 个百分点 |
| 100 | 1 个百分点 |
| 200 | 0.5 个百分点 |

当前 n = 20：**5 个百分点以内的差异在这套集合上不可分辨**。而 95% 区间还会更宽
（首份基线里 Recall@5 的区间是 55%–95%，宽 40 个百分点）。所以：

> 在这套集合上，「没退化」只能由**逐条命中集合**（`hits5` / `hits12` 与 `querySet.sha256`）证明，
> 不能由比例单独证明。比例是给人看的摘要，逐条命中才是判据。

## 三、能测什么

1. **召回路径改动的方向**：同一库、同一查询集，改动前后跑两次，比 `hits5` / `hits12` 与
   逐条命中集合。改动让命中集合变了，就说明它确实动了召回 —— **负对照**就是这么做的（见第八节末）。
2. **与语义无关的旋钮的灵敏度**：`--k-vec` 这类旋钮一改，指标应当动。
   不动说明装置在测别的东西（例如缓存了旧结果）。
3. **耗时量级**：p50/p95 能发现数量级回归（例如把暴力点积换成了每次读库）。
   它不是性能分析工具：44 次调用的分位数，噪声在毫秒级。
4. **两次跑的是不是同一份库**：`atoms` 与 `superseded` 就是随结果一起写的库指纹。
5. **可复跑**：除耗时与 `sha`，两次输出逐字节一致（见第七节）。

## 四、测不出什么

1. **「记忆能力」本身**。这是检索指标：它只看「该来源切出的 atom 是否进前 k」，
   不看模型有没有用这条记忆、不看注入文本读起来怎么样、不看回答对不对。
2. **真实使用下的效果**（见第六节）。
3. **写入路径**：合并判据、主题粒度、`flags`、取代关系。基准只调 `recall`，写入侧改动测不到。
4. **规模效应**：当前库 1374 条 atom。词面与向量路的候选上限（`K_VEC` 等）固定为常数，
   库更大时的退化不会被这套装置发现。
5. **换模型后的可比性**：模型写死在脚本里。换模型即换装置，历史数字全部作废。
6. **小于最小可分辨差的差异**（见 2.4）。
7. **长会话 / 多轮对话记忆**：需要先把会话切成记忆卡，而切法本身是一个可调点；
   不固定切法就测，测的是切法不是插件。
8. **跨机器性能**：p50/p95 只在本机可比。

## 五、语料来源、版本锁定与使用限制

### 5.1 来源：主 LongBench、辅 LongMemEval、不接 LoCoMo

| 用途 | 数据集 | 许可 | 为什么 |
|---|---|---|---|
| 主 | LongBench（`THUDM/LongBench`） | 仓库 MIT（代码与自造标注） | 中文长文本评测，含检索类任务，与「从库里找一段」最接近 |
| 辅 | LongMemEval（`xiaowu0162/LongMemEval`，ICLR 2025） | MIT | 长会话记忆问答，用来对照「记忆型」任务上的行为 |
| 不接 | LoCoMo（`snap-research/locomo`，ACL 2024） | CC BY-NC 4.0 | 非商业限制：vendored 分发等于替所有下游用户背书商业使用 |

**许可的一条关键区别**：仓库标 MIT 只约束代码与整理方式，**语料正文的版权不因此改变**。
LongBench 的 context 分三类：维基派生（CC BY-SA，可再分发）、学术语料（各自条款）、
未清区（新闻正文、网页段落、代码仓库等，本体版权保留）。既然本仓库不重分发（5.4），
许可只影响「复现者能不能合法取用」，不影响本仓库的发布形态 —— 但这要求**不 vendored** 落到实处。

### 5.2 被拒绝的数据形态（以及为什么）

| 形态 | 处置 | 理由 |
|---|---|---|
| 语料本体进仓库（vendored） | 拒绝 | 仓库只含工具链与评测逻辑；许可分层也不允许整包再分发 |
| 仓库里放下载/拉取脚本 | 拒绝 | `bench.mjs` 只接受本地路径。CI workflow 允许做环境准备，但那是 workflow 的位置，不进工具链、不进 npm 包与 dist，产物（库/缓存）不回仓库 |
| 直接把问答数据整包当记忆库 | 拒绝 | 那会把「切卡口径」混进指标；切法不固定，测的是切法 |
| 把无关查询算进 recall 分母 | 拒绝 | 分母里没有它的 target，算进去就是假准确；它们只贡献耗时 |
| LoCoMo | 不接 | 许可是非商业，与本仓库的分发形态冲突 |
| 用基准对外声称「记忆能力」 | 禁止 | 判据 4：它是内部对照，不是能力证明（见第六节） |

### 5.3 版本锁定：三件都要写进结果

复现者在自己的结果里记录（本仓库的结果 JSON 已预留位置）：

1. **语料 commit**：仓库地址 + 完整 40 位 sha，不是分支名（分支会动）；
2. **文件校验和**：每个用到的数据文件的 sha256；
3. **装置侧**：查询集文件的 sha256（`querySet.sha256`，脚本自动算）、建库规则名
   （库的 `build_info` 表里 `entry_rule`，如 `bigram-idf-v4`）、结构版本。

**本仓库当前没有 LongBench 基线**，所以上面第 1、2 项还没有具体值。
这里刻意不写未经核对的 commit 与校验和：写一个查不回来的 sha，比空着更坏 ——
读者会当真去用。

### 5.4 使用限制：不重分发

- 语料及其派生文本（切片、切出来的 atom 文本、查询原文）**不得**出现在：仓库、`dist/`、
  npm 包、发布产物、结果 JSON 里。
- 结果 JSON 只放**聚合指标**与 sha256：不放查询文本、不放 atom 文本、不放机器路径。
  `bench/results/` 里的文件因此可以进仓库。
- 引用上游时按上游要求署名；不把语料再分发。
- 对外沟通中，本基准的数字只能写成「同一装置上的内部对照」，不得写成能力结论。

## 六、与真实使用分布不同

这一节是判据 4 要求的「与真实使用分布不同」的正文。**谁拿它对外宣称记忆能力，谁就越界。**

1. **查询不同**：基准的查询是评测者写的完整问句；真实查询更短、更口语、常依赖上文，
   而且经常是「我记得有这么一条」式的模糊指代。
2. **库不同**：基准库是一次批量导入的固定文本；真实库是逐步写入的短卡片，
   会被改写、被取代（`superseded`）、会跨 scope。当前基准库的 `superseded` 为 0，
   而真实库里「已被取代」的条目恰恰是排序要处理的东西。
3. **相关性定义不同**：基准用「来源相同」判对，真实是「这条对眼下这个问题有帮助」。
   同一条来源切出的多条卡里，可能一条有用、一条没用；基准都算对。
4. **形态不同**：公开集是长会话/长文档，本插件面向短卡片。拿长文档跑出来的数字，
   不代表短卡片上的表现，反之亦然。
5. **没有多轮**：每次查询独立，没有上下文累积、没有「上次问了什么」的影响。

**可比的边界**：数字只在「同一装置、同一子集、同一库」内可比；
跨装置、跨模型、跨数据集的比较都没有意义。

## 七、复跑与逐字节比对

脚本**故意不写时间戳**：写了就等于每次都不一样，逐字节比对立刻失效。
两次跑之后，按下面的方式去掉会变的字段再比（用 `console.log` 输出，避免转义）：

```bash
node -e "const fs = require('node:fs'); const j = JSON.parse(fs.readFileSync(process.argv[1], 'utf8')); delete j.sha; delete j.p50_ms; delete j.p95_ms; console.log(JSON.stringify(j, null, 2))" run-1.json > run-1.stable.json
node -e "const fs = require('node:fs'); const j = JSON.parse(fs.readFileSync(process.argv[1], 'utf8')); delete j.sha; delete j.p50_ms; delete j.p95_ms; console.log(JSON.stringify(j, null, 2))" run-2.json > run-2.stable.json
diff run-1.stable.json run-2.stable.json && echo 完全一致
```

结果文件命名：`bench/results/<被测提交号>.json`。**这个提交号指的是被测量的那份代码**
（其 `src/` 编出的 `dist/` 就是跑出这组数字的产物），不是「把结果文件提交进去的那个提交」——
后者在跑的时候还不存在。

## 八、当前基线（内部子集，非公开语料）

首份基线用本机内部数据跑：库 1374 条 atom、查询集 44 条（20 条带 target、24 条无关查询）。
结果见 `bench/results/` 下与提交号同名的那份 JSON。要点：

- Recall@5 = 0.75、Recall@12 = 0.95（分母 20 条）；
- 耗时 p50 约 7 ms、p95 在 9–15 ms 之间（44 次 recall 调用，不含编码，本机采集；
  两次跑的数不同，这正是耗时字段被排除在逐字节比对之外的原因）；
- 95% 区间：Recall@5 约 55%–95%、Recall@12 约 85%–100%；
- 最小可分辨差 = 5 个百分点（1/20）。

**这套内部子集的查询集不入库**（它带内部路径）。要用它复跑，需要评测者自己持有同名查询集，
并用 `querySet.sha256` 核对是不是同一份。

### 负对照：证明装置真的在测召回

**做法**：把 `--k-vec` 拧到 1（向量粗筛只剩一条），指标必须下降。

```bash
# 默认
node scripts/bench.mjs --db <库> --queries <查询集> --out a.json
# 负对照
node scripts/bench.mjs --db <库> --queries <查询集> --k-vec 1 --out b.json
```

**实测（2026-10-18，同一份 1374 条库、20 条带 target 的查询）**：

| 旋钮 | Recall@5 | Recall@12 | Recall@12 的 95% 区间 |
|---|---|---|---|
| 默认 | 75.0%（15/20） | **95.0%（19/20）** | [85%, 100%] |
| `--k-vec 1` | 75.0%（15/20） | **75.0%（15/20）** | [55%, 95%] |

Recall@12 掉 20 个百分点（少 4 条命中），Recall@5 不动——头部 5 条本来就由入口与词面两路覆盖，
这条集合对向量路宽度的灵敏度只体现在中段。**知道它不灵敏，比假装它灵敏好**：
要它同时对 @5 敏感，得把 n 做大（见第四节「测不出什么」）。

结果 JSON 里 `kVec: null` 表示默认行为、`kVec: 1` 表示这次走了负对照——两次跑的差异因此可解释。
