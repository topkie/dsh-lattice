# dsh-lattice 设计原则

本文件是**根本约束**：任何设计决定与它冲突时，改决定，不改它。
改动它需要明确理由，并在提交信息里说明；文件自身的修订历史见仓库提交记录。

---

## 一、主原则

> **模型管内容，插件管形式；模型管语义，插件管结构。**

更精确的表述（同时约束「谁判」与「何时判」）：

> **语义判断只在写入现场发生一次，插件侧全是几何运算。**

两句话是同一件事。后者更严格，因为「时机」那一半是若干设计的依据——
例如把切分候选留到下次召回时确认，之所以成立，正是因为它没有违反「只发生一次」，只是把「哪一次」选了更省 token 的那次。

**它的非预期收益**：整套系统可重算、可解释、可回滚——因为它不含任何「模型的意见」。

---

## 二、三层原理

| 原理 | 作用环节 | 一句话 | 落在哪个字段 |
|---|---|---|---|
| **知识正交** | 注入 | 一份知识只存一份，省 token，且消除「相似但不一致」的隐性冲突 | 正文 |
| **入口冗余** | 召回 | 同一个意思要有多种说法作入口，否则换述即失联 | Entry 表 |
| **链接显式** | 推理 | 不同意思之间的关系必须写出来，模型自己连不上 | Edge 表 |

三条**不冲突，因为物理分离**：正文管正交、入口管冗余、边管关系，机制上无法互相污染。

**支点**：入口不参与正交判定——它让「加入口」永远不必担心污染正交度。

## 三、职责分工

| 判断 | 归谁 | 何时 | 插件提供什么 |
|---|---|---|---|
| 这是**几件事**（切分点） | 模型 | 使用现场确认 | 自洽度评分给候选 |
| 这两件事**什么关系**（边类型） | 模型 | 写入现场确认一次 | 规则 + 向量取候选 |
| 这两条**是不是一件事**（落位） | **插件提议，模型可否决** | 写入现场 | 余弦 + 词面两票 |
| **怎么存 / 怎么找 / 怎么注入** | 插件 | 全程 | —— |

「落位」是唯一由插件**独立下结论**的语义判断，这是刻意的：它必须发生在写入路径上，且不能依赖「模型每次都有空细看」。
所以它用两票（余弦 + 词面）降低误判，并把歧义标出来交给模型。

### 边界一：迁移 / 导入的判决归模型

格式解析归脚本，语义判决（哪些内容算一条记忆、原子边界在哪）归模型，存储形态归插件。
把语义判断下沉到形式层会产生两种后果：判据不可移植（只对某一类来源格式有效），以及粒度由来源格式而非语义决定。

### 边界二：所有权与删除权限（非对称）

**前提**：记忆内容的所有权归模型，但**运行记忆的机器与机器上的数据归用户支配**。
所以模型的自主权只覆盖**内容**，不覆盖**数据**。

| 权限 | 模型 | 用户 |
|---|---|---|
| 写入 / 声明取代 / 标记失效 | ✅ 自主 | ✅ |
| 降权 / 冻结（可逆） | ✅ 插件执行 | ✅ |
| **物理删除** | ❌ **只能提议** | ✅ 所有者 |

价值在于：所有不确定的判断都只影响可见性，误伤后果从「信息永久丢失」降为「排序靠后」。

**非对称是刻意的**：用户是所有者，他的指令本身就是完整授权，**不该再问「确定吗」**；
模型不是所有者，所以它只能走到「可逆的中间态」。也因此，**「删除必须是显式的管理动作」指「用户说了才删」，
而不是「每次删除都要用户过闸」——过闸的对象是模型的操作，不是用户的意图。**

要防两件事：**模型误删**（它本就没有这个权限），以及**用户删除后内容被重新写入**
（靠删除留痕 + 内容指纹比对）。

### 边界三：本插件不对什么负责

本插件只对**自己的行为**负责。

| 事项 | 归谁 |
|---|---|
| 插件的行为是否正确 | 本插件 |
| 宿主 API 的行为、工具链的报错 | 宿主 / 工具链 |
| 网络、缓存、平台等环境条件 | 环境 |

对后两者，插件只做两件事：**声明自己依赖什么**，以及在**真实环境里验证一次**。
**不为它们兜底。**

## 四、无 LLM 推出的结构性结论

**(1) 没有 hook，只有 tool。** 禁用 LLM 就做不了「轮次结束自动蒸馏」，插件形态由此确定。
**推论：写入纪律就是系统质量。** 没有自动兜底，写入契约必须做到「全默认也能工作」，否则模型一旦偷懒，整条管线就退化。

**(2) 插件侧全是几何运算。** 定位（余弦）、切分候选（自洽度）、边候选（规则 + 向量）——没有任何一步需要理解。

**(3) 取消物理分库。** 同一份知识在多个库各存一份会直接破坏正交 → 改为 atom 带 scope、检索时过滤、全局域复用。

## 五、四条行为边界

| 边界 | 含义 |
|---|---|
| **按需注入，不自动注入** | systemPrompt 只给极简说明 + 一行库现状，**不注入任何记忆内容**；内容必须走 `lattice_recall` |
| **显式动作** | 写入与召回都是显式动作，不设自动触发 |
| **可以降级，但必须留痕** | 任何降级都要落到 `View.meta` 或健康指标上，**不允许静默失效** |
| **不确定处不做二值判断** | 判据的输出应决定「给多少」，而不是「给不给」 |

第四条的推导：判据所依赖的量会随语料漂移，即判据本身不确定。二值门槛在判错时非全给即全不给；
分档在判错时只是相邻档位的效率损失。**能用分档就别用门槛。**

## 六、数据边界

| 原则 | 内容 |
|---|---|
| **真相源唯一** | 只有 atom 本体、declared 边 / 归属 / 入口不可重算；topic / domain / extracted 与 learned 入口 / 全部索引都可由 atom 重算 |
| **存储单位 ≠ 注入单位** | 存储与召回在 atom 粒度（细、正交、命中率高），注入按 topic 组装（按预算挑选） |
| **入口不参与正交判定** | 加入口的多少永远不影响正交度 |

---

## 七、刻意放弃的三件事

**不要把成本藏起来**——放弃是因为代价已经量过，不是因为做不到。

| 放弃 | 原因 | 替代 |
|---|---|---|
| 自动拆分 | 切分点是理解，不是几何 | 自洽度评分给候选 + 异步确认 |
| 自动冲突检测 | 基于规则的判定不可行 | 同 Topic 多 Atom 同时可见，由写入方发现 |
| 主题命名可读性 | 无 LLM 无法生成好标题 | 标题只当检索入口，可读性由 `atom.summary` 承担 |

---

## 八、用这些原则自检

提出一个改动时，依次问：

1. 它是否把某个**语义判断**挪进了插件？（违反主原则）
2. 它是否让某个**派生物**变成了真相源？（违反真相源唯一）
3. 它是否让**入口**影响了正交判定？（违反支点）
4. 它是否在某处**静默降级**？（违反必须留痕）
5. 它是否用**二值门槛**处理一个会漂移的量？（违反第四条行为边界）
6. 它是否让插件**承担了它没有的能力**（例如主动提醒）？
7. 它依赖的**量**在目标场景里真的存在吗？（小样本、导入、冷启动场景尤其要问）
