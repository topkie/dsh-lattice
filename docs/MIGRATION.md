# 从其他记忆库迁入 dsh-lattice 的操作规范

> **对应版本**：以 `package.json` 的 `version` 为准（运行时可用 `lattice_ping` 读）。换版本要重核 §7 与全部阈值。
> **读者**：执行迁移的 agent，以及给它下指令的人。**每节末尾的「agent 检查表」是给前者照做的**，正文是给后者判的。
> **术语**：本文的「atom」就是一条记忆（工具返回的 `#37` 是它的编号），「主题（topic）」是记忆的自动归组，
> 「入口（entry）」是一条记忆参与检索的说法；五个工具与召回输出的含义见 [接入文档](INTEGRATION.md) 第 5 节的术语表。
> **证据强度**：**实测**来自一次真实迁移（若干百条规模，见附录）；**推断**是从目标库的设计与实测外推的，未验证。
> 没有标「实测」的判断按推断读。

---

## 0. 这份规范管什么

**管**：把已有记忆条目从别的库搬进 dsh-lattice 时 —— 数据怎么组织、流程怎么走、怎么验收、怎么收尾。
**不管**：dsh-lattice 的安装与配置；也不是「怎么写记忆」的通用教程（那件事看目标库自己的写入规程）。

**三条前提，先说清，否则后面全是误解**：

1. **迁入即生效。** 目标库没有审核层。迁进来的内容**立刻可被召回**，不存在「等人批一下才生效」的中间态。
2. **模型侧没有删除权。** 目标库给模型的工具里没有 forget/delete —— 删除按钮在界面上，那是刻意的设计（物理删除归用户）。**所以迁入基本上是不可逆的。**
3. **迁完不会自己长，也不会自己变干净。** 目标库只有工具、没有 hook，没有「轮次结束自动沉淀」；也没有淘汰与时间衰减机制。

**[agent 检查表 0]**

- [ ] 确认目标库版本：`lattice_ping` 的 `version`
- [ ] 确认自己手里只有 `lattice_*` 五个工具，其中**没有** forget / delete
- [ ] 确认源库能**全量导出**（只能翻界面的库不要迁）

## 1. 迁之前：该不该迁

**判据不是「能不能导出」，而是「迁进去以后，每一条还能被正确召回吗」。**

五项前置检查：

| # | 查什么 | 答不上来的后果 |
|---|---|---|
| 1 | 源库各状态各有多少条：主库 / 待审 / 草稿 / 已删除 | 不知道迁多少，也不知道漏了什么（§6.1） |
| 2 | 源条目的粒度：多数是「一张卡带分节」还是「一句一条」 | 前者会被按句切分，条数会明显变多（§3.2） |
| 3 | 源库有没有**稳定 ID** | 没有就拿不到幂等对照表，重跑必重复（§4.4） |
| 4 | 迁移期间源库**还会不会写入** | 会动就必须冻结或写双写规则（§6.2） |
| 5 | 目标库是空的还是已有内容 | 已有内容会影响主题落位（§4.2） |

**这五项里任何一项答不上来，就先别迁** —— 迁移的代价是它不可逆。

**[agent 检查表 1]**

- [ ] 数出源库每个状态的条目数，写下「本轮迁哪一档、其余为什么不迁」
- [ ] 抽 3 条源条目，判断是「多主题卡」还是「单结论」
- [ ] 确认源库有条目 ID；没有就先建
- [ ] 确认源库在本轮迁移期间是否还会写入

## 2. 目标形态：迁进来的数据长什么样

这一节是**判据**，不是格式偏好 —— 每一条不满足都有具体后果。

| 要素 | 要求 | 不满足会怎样 |
|---|---|---|
| **正文** | 一条一句结论 | 多主题挤一条 → 主题落位算不准，召回时整条被拖出来 |
| **长度** | ≤ 600 字 | 超过会被**按句自动切**成多条，语义在切点处分离；超过 8 段（很长的卡）会整条**拒收**、一条都不写，要先自己按主题拆成多次写入 |
| **首句** | 要能独立说明这条在讲什么 | 目录视图的摘要取正文**第一句**（按句末标点切，最多 48 字）：第一句是半句，列表里就是半句；正文整段只有表格或围栏代码块时摘要为空，列表里看不见内容 |
| **kind** | 结论 / 坑 / 命令与参数 / 环境 / 步骤 / 数据，六选一 | 认不出的值按「结论」记，并在写入回执里说明；历史值「参数」写入时归一到「命令与参数」，查询时两者都匹配 |
| **refs** | 用户以后会怎么问：问法、俗称、报错原文 | 入口词先从正文里自动抽（之后还会从使用中学），正文里没有的说法（俗称、报错原文）不会自己出现 → 用户按自己的叫法问就找不到 |
| **scope** | `global` 或项目键 | 项目事实混进 global 会污染所有项目 |
| **origin** | 导入的标 `import` | 以后分不清「外部导入的」与「自己总结的」 |

**为什么「首句要能独立说明这条在讲什么」要写进规范**：它看起来是文风，实际是**可见性**。
摘要不是另存的一份，是从正文里抽的第一句；第一句是半句，目录里就是半句。实测里出现过
「有内容、但目录视图里是空的」atom —— 不是坏了，是去掉 Markdown 装饰之后没有可摘的句子
（整段只有表格或围栏代码块）。写这类内容时，前面补一句普通句子。

**[agent 检查表 2]**

- [ ] 每条 atom 的正文都能用一句话概括
- [ ] 没有一条超过 600 字（超了就主动拆，不等写入侧切）
- [ ] 每条第一句都能独立当摘要
- [ ] kind 只用六类；refs 不是空的；scope 与 origin 都给了

## 3. 映射：源 → 目标

### 3.1 能映射的六项

| 源 | 目标 | 说明 |
|---|---|---|
| 一张卡 | **一到多条 atom** | 超过 600 字的卡会被按句切，不超长的卡就是一条；条数可能变多，这是设计不是错误 |
| 目录分类 | `kind`（六类）+ `scope` | 粒度**必然变粗**，认了它 |
| 标签 tags | `refs` + 正文 | `refs` 会变成这条记忆的入口词，入口词参与词面检索（别名、俗称、报错原文写进 `refs`，否则那种说法命中不了）；正文本身也在检索范围里 |
| 人工「见 X 卡」 | 优先写成**声明边**（`lattice_write` 的 `edges`，`origin` 为 declared）；说不清关系的只进正文一句 | 声明边是真相源，重建后仍在；交给自动 edge 的话它是**推断**的，重建会整批换掉，也不承载「为什么指过去」 |
| 修订关系 | `supersedes` | 旧条留痕不删 |
| 时间戳 | 不搬 | 目标侧只记「写入时刻」，源库的「最后更新」没有位置 |

### 3.2 不可映射的四项（必须逐项交代）

| 丢失的 | 处置 |
|---|---|
| **标题分级层级** | 拆成多条 atom，每段第一句要能独立成句（目录里显示的摘要就是第一句）。**别指望目标侧恢复层级** —— 它没有这个结构 |
| **目录的语义**（如 Mistakes / Knowledge） | 折进 `kind`；折不下就并入默认类，**并在迁移记录里点名** |
| **人工链接的语义**（为什么指向它） | 只能进正文一句话。edge 只记「有关系」，不记「什么关系」 |
| **条目顺序 / 目录树** | 不保留 |

### 3.3 分类必须有默认类

源库的 kind / tag 体系往往和目标六类对不上。规范要求：**先写死一张映射表，再指定一个默认类**（映射不到的都归它）。
默认类要写进迁移记录 —— 事后才查得出「哪些是硬塞进来的」。

**[agent 检查表 3]**

- [ ] 完整 kind 映射表（含默认类）已写下
- [ ] 「不可映射项」四项各有处置
- [ ] 抽 5 条源条目试映射，确认没有落不下的

## 4. 执行

迁移只有一个通道：逐条调 `lattice_write`（模型侧工具）。本仓库**没有**批量导入的命令、脚本或路由 ——
「迁一条」就是一次工具调用，每条都要过一遍长度审核、重复检测与主题落位；批的大小因此受调用次数限制。

### 4.1 先小批试迁，别一次全量

先迁 5~10 条，然后把它们**召回一遍**。小批就能暴露：超过 600 字的卡是不是在切点处断了语义、主题落位是否合理、refs 够不够。
全量迁完再发现这三件事，成本是重迁 —— 而重迁本身会产生重复。

### 4.2 分批顺序会决定主题结构

目标库的主题是**写入时几何落位**的：先写的形成主题，后来的往里并或新建。**同一批数据换个顺序，迁完的主题树不一样。**
所以：**按源库天然的簇（目录 / 标签）成组迁**，不要按时间序或字母序。

### 4.3 状态筛选：只迁主库

理由在 §6.1：迁入即生效。源库里没过审的内容，迁进来就等于**自动通过**了。
**定案：只迁「主库 / 已批准」一档；待审 / 草稿 / 已删除一律不迁**（源库没有审核层时，全部条目视为主库）。
不迁的那部分要写进记录，不是不写。

理由：迁入即生效（§6.1），「其余状态逐项决定」在实践中会退化成「这次先迁一点」；而源库还在长的时候（§6.2 末），这条例外永远关不上。

### 4.4 幂等：必须建对照表（最容易漏的一条）

迁移会分批、会失败重跑。**没有「源 ID → 目标 atom id」的对照表，重跑就是再迁一遍。**

对照表最少三列：`源 ID | 目标 atom id | 状态`。状态至少三档：已迁 / 跳过（原因）/ 失败（原因）。
它同时是 §5 的验收依据和 §9 的回滚依据。

### 4.5 去重提示怎么判

写入侧遇到相似内容会给一条**提示**（不阻止写入）。它有两种含义，必须人工判一次：

- **同一件事** → 收成一条（后写的标 `supersedes` 指向先写的）；
- **同一主题下的相邻结论** → 两条都留，忽略提示。

把它一律当「重复」删掉，会丢掉本来该有的相邻结论。

**[agent 检查表 4]**

- [ ] 已试迁 5~10 条并召回验证
- [ ] 分批按源库的簇分组，不是按时间序
- [ ] 只迁主库；其余状态有书面理由
- [ ] 对照表三列齐备，状态三档齐备
- [ ] 每条去重提示都判过一次（同一件事 / 相邻结论）

## 5. 验收：四条判据，每一条都要「能红」

| # | 判据 | 怎么测（**要写成能构造失败的形式**） |
|---|---|---|
| 1 | 源库主库条目**每一条**都写过 | 对照表行数 = 源条目数且失败为 0；**再随机抽 3 条源 ID 反查目标 atom** —— 只对计数不算验 |
| 2 | atom 增量**可解释** | 预期 = 源条目数 × 平均切分数。偏差超过两成就去查：切分阈值变了？还是有条目被静默跳过？ |
| 3 | 抽样**能召回** | **抽源库里最冷门的条目**，用它的原话去召回。抽显眼条目一定命中 —— 那是恒真判据 |
| 4 | 源库**未被动过** | 迁移前后各取一次源库统计，必须相同；全程只调读接口 |

**判据 2 为什么重要**：粒度从「卡」变成「句」，条数翻倍是**正常的**。不知道这件事的迁移者会把「变多了」当成错误去修 ——
而正确的反应是「多了多少，能不能用源条目数解释」。

**判据 4 的边界**：迁移是**单向复制**。顺手在源库上「整理一下」的那一刻，这条判据就不成立了，也没法再验。

**[agent 检查表 5]**

- [ ] 对照表行数对得上，失败清单一并交出
- [ ] 随机 3 条源 ID 反查到了目标 atom
- [ ] atom 增量算得出解释（不是「差不多」）
- [ ] 抽样用的是**冷门**条目，且命中了
- [ ] 源库统计前后一致

## 6. 收尾

### 6.1 迁入即生效：两个必须交代的后果

1. **源库里没过审的内容，迁进来就等于自动通过。** 这是 §4.3「只迁主库」的全部理由。
2. **没有「撤一下」这回事。** 见 §9。

### 6.2 冻结源库（定案）：双写期只在四条齐备时允许

源库还活着就会**漂移**，而迁移是快照。**定案：默认冻结。**

- **默认做法：冻结。** 迁完即宣告源库只读或下线，写进迁移记录。
- **例外：双写期。** 只有同时满足下面四条才允许：
  1. 源库短期无法下线（它还在服务别的用途）；
  2. **哪边是权威**已写明（一条冲突时按哪边算，写进记录）；
  3. 双写的**截止时间**已写明，到点退化为冻结；
  4. **冲突怎么合**已写明（以哪边覆盖，还是两条都留并用 `supersedes` 标出取代关系）。

  缺任何一条，就按默认冻结做 —— 缺一条的双写期，最后都会变成两份记忆各长一套事实。

**理由**：双写期的成本不在「两边都写」，在冲突合并；而「哪边对」正是 §3 那套语义判决要处理的事，
迁移期间没有额外的人手逐条做。冻结一次，代价是源库停用；双写一次，代价是两套事实长期并存。

**还有一条来自实测的提醒**：如果源库有「自动沉淀」这类机制，它每轮都在长 —— 那么**「把待审的都迁完」是移动靶**。
要么定时点迁（并写明迁的是哪一刻的快照），要么先冻结再迁。

### 6.3 迁完当天就切换写卡模板

迁入的是「一句一条记忆」，如果之后还按「一张卡一主题」写，库会当场分成两半 —— 而那时没人记得该用哪套。

做法：把新形态写成**一条规范记忆卡放进库里**（它自己也会被召回），迁移记录里写明「从第 N 条 atom 起按新形态」。

### 6.4 落记录（最少四样）

| 记什么 | 为什么 |
|---|---|
| **源库快照**：时间、各状态条目数、导出的来源 | 以后要证明「迁的是哪一刻」 |
| **映射表**：kind 映射 + 默认类 | 解释「为什么这条归在这类」 |
| **对照表**：源 ID → atom id | 校验、去重、回滚都靠它 |
| **遗留决定**：没迁的状态、没解决的半过时内容 | 不写就等于失忆 |

**[agent 检查表 6]**

- [ ] 源库的处置（冻结/双写）写进记录了
- [ ] 新写卡形态已成一条库内规范卡
- [ ] 四样记录齐备

## 7. 局限（对应本文写作时的版本）

| 局限 | 对迁移者的影响 | 要做的事 |
|---|---|---|
| **LLM 无删除权** | 迁错了不能自愈 | **迁前备份目标库**（这是操作，不是建议） |
| **无淘汰 / 时间衰减** | 旧结论一直在，而且照样会被召回 | 只能靠 `supersedes` 手动退役，且**要定期做** |
| **无自动沉淀** | 库不会自己长 | 迁完 ≠ 以后都会记得；写入必须由 LLM 主动发起 |
| **主题层可能退化** | 实测单 atom 主题占比超过三分之二 | 主动用 `topic_hint` 聚；**别指望迁完它自动成型** |
| **edge 稀疏** | **自动推断的**关系基本不工作；模型可以用 `edges` 显式声明关系，声明的那部分会参与图路扩展（把邻居带进候选） | 别指望靠自动推断的图路把内容找回来；已知的关系要显式声明（§3.1），否则重建后没有 |
| **单机单库** | 没有并发写入的实测依据 | 迁移时别开着别的会话大量写 |
| **编码器依赖模型文件** | 首次使用要能拿到模型（先试 `huggingface.co`，再试 `hf-mirror.com`） | 离线环境先确认已缓存，或让两条源中的一条可达 |
| **常量上限** | 图推断有条数上限（数千量级）；列表分页有硬上限（50） | 超大库分批验，别一次拉全量 |

**这一节要随版本改。** 上面每一条都是「当前实现」的事实，不是永久设计。

## 8. 假象：目标库和源库不一样，会造成的误判

| 看起来像 | 实际是 | 怎么验 |
|---|---|---|
| 写入成功 = 迁好了 | 只说明落了库 | 抽样召回（§5 判据 3） |
| 条数没少 = 没丢知识 | 一句结论会把上下文切断，语义在切点处分离 | 用源库**冷门**条目抽，逐条读 |
| 有主题 = 组织起来了 | 主题可能只装一个 atom | 看主题规模分布 |
| 目录里是空的 = 那条没内容 | 摘要抽不出句子（正文只有表格或代码块），或第一句被截成半句 | `lattice_expand` 看全文 |
| 相似度提示 = 重复 | 也可能是同一主题下的相邻结论 | 人工判一次（§4.5） |
| 取回次数高 = 这条重要 | 那只是**谁在查**留下的痕迹 | 别看这个指标 |
| 磁盘上的版本 = 实际生效的版本 | 进程可能还跑着旧的 | 看 `lattice_ping` 的 version |

**另有一条不算假象、但常被误解**：`origin=import` 是**来源标记**，不是质量标记。导入的条目不会因此更不可信，也不会因此更权威。

## 9. 回滚与不可逆

**迁入基本不可逆** —— 模型侧没有删除权（§0 前提 2）。真出问题时，现实路径只有三条：

| 路径 | 代价 |
|---|---|
| 用户在界面上逐条删 | 量大时不可行 |
| 用备份覆盖目标库 | 会连迁移后新写的一起丢 |
| **不撤销，写新条 `supersedes` 覆盖**（定案：默认走这条） | 最省，但库里会留下一批「被取代的迁入条」 |

**所以：迁移前先备份目标库。** 备份这件事写在流程里，不要留在记忆里。

**三条路径的定案**：默认走「写新条 + `supersedes` 覆盖」——它是唯一不丢迁移后新写内容的路径；
「备份覆盖」只在**整批迁错**时用（它会连迁移后新写的一起丢）；「界面逐条删」不作为批量手段（量大时不可行，
而且模型侧本来就没有删除权）。

**[agent 检查表 9]**

- [ ] 目标库已备份，备份位置写进迁移记录
- [ ] 已确认撤销只有三条路径（界面逐条删 / 备份覆盖 / supersedes 覆盖）
- [ ] 已告知发起人：**迁入不可逆**

## 10. 迁移路线的定案

本节把几处容易临场改主意的选择逐条定下来。这里的「路径」指**迁移路线上要做的选择**，不是文件路径。
每条的完整写法在对应小节，这里只做索引与一句话理由。

| # | 问题 | 定案 | 理由（一句） |
|---|---|---|---|
| 1 | §4.3 主库之外的条目怎么办 | 待审 / 草稿 / 已删除**一律不迁**；不迁的那部分写进记录 | 迁入即生效，「逐项决定」会退化成「先迁一点」，而源库还在长的时候这条例外永远关不上 |
| 2 | §6.2 冻结，还是双写期 | **默认冻结**；双写期只在四条齐备时允许（哪边权威、截止时间、冲突怎么合、源库暂时无法下线） | 双写的成本在冲突合并，而判断「哪边对」正是迁移期间最缺人手做的那件事 |
| 3 | §3.1 人工链接（「见 X 卡」）怎么办 | 优先写成**声明边**（`edges`）；说不清关系的只进正文一句 | 声明边是真相源（重建后仍在），自动 edge 是派生物（重建会整批换掉） |
| 4 | §9 撤销走哪条路 | 默认「写新条 + `supersedes` 覆盖」 | 三条里只有它不丢迁移后新写的内容 |
| 5 | 目标 kind 分几类 | **六类**（结论 / 坑 / 命令与参数 / 环境 / 步骤 / 数据） | 实现与本文都按六类；版本号以 `package.json` 为准 |
| 6 | §7 说 edge 稀疏，实际情况 | 推断边仍稀疏；**声明边可用** | 显式声明的关系会参与图路扩展，是迁移时保住关系的唯一手段 |

**明确不做的事**：

- **不做「迁完自动重建主题」**：主题与其它派生物都能重算，但重算不改善落位；把它当迁移收尾步骤，会掩盖 §4.2 的分批顺序问题。
- **不做源库与目标库的自动比对**：验收判据（§5）刻意要求人抽冷门条目；自动比对只能证明「计数对得上」。
- **不在迁移时改目标库的阈值**：阈值是全局配置；为一次迁移改它，等于让此后所有写入都按这次迁移的数据分布走。

## 附录：一次真实迁移的轮廓（已脱敏）

| 项 | 情况 |
|---|---|
| 源库形态 | 卡片式：一张卡一个主题、带分节、正文有长度上限、**有审核层** |
| 源库规模 | 约百条主库；另有少量待审/已删除条目 |
| 迁移后 | atom 数**约翻倍**（按句切分造成）；主题数接近 atom 数（主题退化） |
| 执行 | 分 4 批，每批数条到数十条；全程只读源库 |
| 踩到的坑 | ① 分类映射的默认类没定 → 留下一个非法 kind；② 有 atom 的摘要抽不出来 → 目录里看不见内容；③ 「把待审的都迁完」是移动靶；④ **第一轮判据漏掉了一类「半过时」内容** |

**关于第 ④ 条，要单独说**：迁移后最常见的一类遗留，不是「服务没了」，而是**「方法看着通用、约束已经换了一套」**。
只用「服务还在不在」去筛，一定漏。判据要加上：**照它做会不会错**。
