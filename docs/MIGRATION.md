# 从其他记忆库迁入 dsh-lattice 的操作规范

> **对应版本**：dsh-lattice `0.2.0-dev`。换版本要重核 §7 与全部阈值。
> **读者**：执行迁移的 agent，以及给它下指令的人。**每节末尾的「agent 检查表」是给前者照做的**，正文是给后者判的。
> **证据强度**：逐条标注 —— **实测**来自一次真实迁移（若干百条规模），**推断**是从目标库的设计与实测外推的，未验证。

---

## 0. 这份规范管什么

**管**：把已有记忆条目从别的库搬进 dsh-lattice 时 —— 数据怎么组织、流程怎么走、怎么验收、怎么收尾。
**不管**：dsh-lattice 的安装与配置；也不是「怎么写记忆」的通用教程（那件事看目标库自己的写入规程）。

**三条前提，先说清，否则后面全是误解**：

1. **迁入即生效。** 目标库没有审核层。迁进来的内容**立刻可被召回**，不存在「等人批一下才生效」的中间态。
2. **模型侧没有删除权。** 目标库给模型的工具里没有 forget/delete —— 删除按钮在界面上，那是刻意的设计（物理删除归用户）。**所以迁入基本上是不可逆的。**
3. **迁完不会自己长，也不会自己变干净。** 目标库只有工具、没有 hook，没有「轮次结束自动沉淀」；也没有淘汰与时间衰减机制。

**[agent 检查表 0]**

- [ ] 确认目标库版本：`lattice_ping` 的 `version`
- [ ] 确认自己手里只有 `lattice_*` 六个工具，其中**没有** forget / delete
      （`lattice_feedback` 是样本反馈：它只写独立样本库，不改动任何记忆）
- [ ] 确认源库能**全量导出**（只能翻界面的库不要迁）

## 1. 迁之前：该不该迁

**判据不是「能不能导出」，而是「迁进去以后，每一条还能被正确召回吗」。**

五项前置检查：

| # | 查什么 | 答不上来的后果 |
|---|---|---|
| 1 | 源库各状态各有多少条：主库 / 待审 / 草稿 / 已删除 | 不知道迁多少，也不知道漏了什么（§6.1） |
| 2 | 源条目的粒度：多数是「一张卡带分节」还是「一句一条」 | 前者会被按句切分，条数会明显变多（§3.2） |
| 3 | 源库有没有**稳定 ID** | 没有就拿不到幂等对照表，重跑必重复（§4.4） |
| 4 | 迁移期间源库**还会不会写入** | 会动就必须冻结或写双写规则（§6.2） |
| 5 | 目标库是空的还是已有内容 | 已有内容会影响主题落位（§4.2） |

**这五项里任何一项答不上来，就先别迁** —— 迁移的代价是它不可逆。

**[agent 检查表 1]**

- [ ] 数出源库每个状态的条目数，写下「本轮迁哪一档、其余为什么不迁」
- [ ] 抽 3 条源条目，判断是「多主题卡」还是「单结论」
- [ ] 确认源库有条目 ID；没有就先建
- [ ] 确认源库在本轮迁移期间是否还会写入

## 2. 目标形态：迁进来的数据长什么样

这一节是**判据**，不是格式偏好 —— 每一条不满足都有具体后果。

| 要素 | 要求 | 不满足会怎样 |
|---|---|---|
| **正文** | 一条一句结论 | 多主题挤一条 → 主题落位算不准，召回时整条被拖出来 |
| **长度** | ≤ 600 字 | 超过会被**按句自动切**成多条，语义在切点处分离 |
| **首句** | 要能当标题 | 目录视图取「标题后的第一段」当摘要；没有标题行 → **摘要为空、列表里看不见** |
| **kind** | 结论 / 坑 / 步骤 / 参数，四选一 | 别发明第五类：非法值会一直躺在库里（有实例） |
| **refs** | 用户以后会怎么问：问法、俗称、报错原文 | 检索入口少 → 那条几乎不会被找到 |
| **scope** | `global` 或项目键 | 项目事实混进 global 会污染所有项目 |
| **origin** | 导入的标 `import` | 以后分不清「外部导入的」与「自己总结的」 |

**为什么「首句能当标题」要写进规范**：它看起来是文风，实际是**可见性**。
实测里真出现过「有内容、但目录视图里是空的」atom —— 不是坏了，是它没有标题行可摘。

**[agent 检查表 2]**

- [ ] 每条 atom 的正文都能用一句话概括
- [ ] 没有一条超过 600 字（超了就主动拆，不等写入侧切）
- [ ] 每条第一句都能直接当标题
- [ ] kind 只用四类；refs 不是空的；scope 与 origin 都给了

## 3. 映射：源 → 目标

### 3.1 能映射的六项

| 源 | 目标 | 说明 |
|---|---|---|
| 一张卡 | **一到多条 atom** | 按句切；条数会变多，这是设计不是错误 |
| 目录分类 | `kind`（4 类）+ `scope` | 粒度**必然变粗**，认了它 |
| 标签 tags | `refs` + 正文 | tags 是给字面匹配用的；`refs` 是给向量召回的 |
| 人工「见 X 卡」 | 不搬，交给自动 edge | edge 是**推断**的，不承载「为什么指过去」 |
| 修订关系 | `supersedes` | 旧条留痕不删 |
| 时间戳 | 不搬 | 目标侧只记「写入时刻」，源库的「最后更新」没有位置 |

### 3.2 不可映射的四项（必须逐项交代）

| 丢失的 | 处置 |
|---|---|
| **标题分级层级** | 拆成多条 atom，每段首补一句能当标题的话。**别指望目标侧恢复层级** —— 它没有这个结构 |
| **目录的语义**（如 Mistakes / Knowledge） | 折进 `kind`；折不下就并入兜底类，**并在迁移记录里点名** |
| **人工链接的语义**（为什么指向它） | 只能进正文一句话。edge 只记「有关系」，不记「什么关系」 |
| **条目顺序 / 目录树** | 不保留 |

### 3.3 分类必须有兜底值

源库的 kind / tag 体系往往和目标四类对不上。规范要求：**先写死一张映射表，再给一个兜底类**。
兜底类要写进迁移记录 —— 事后才查得出「哪些是硬塞进来的」。

**[agent 检查表 3]**

- [ ] 完整 kind 映射表（含兜底类）已写下
- [ ] 「不可映射项」四项各有处置
- [ ] 抽 5 条源条目试映射，确认没有落不下的

## 4. 执行

### 4.1 先小批试迁，别一次全量

先迁 5~10 条，然后把它们**召回一遍**。小批就能暴露：切分是否把语义切断了、主题落位是否合理、refs 够不够。
全量迁完再发现这三件事，成本是重迁 —— 而重迁本身会产生重复。

### 4.2 分批顺序会决定主题结构

目标库的主题是**写入时几何落位**的：先写的形成主题，后来的往里并或新建。**同一批数据换个顺序，迁完的主题树不一样。**
所以：**按源库天然的簇（目录 / 标签）成组迁**，不要按时间序或字母序。

### 4.3 状态筛选：只迁主库

理由在 §6.1：迁入即生效。源库里没过审的内容，迁进来就等于**自动通过**了。
默认：**只迁主库/已批准**。其余状态要逐项显式决定，并写进记录。

### 4.4 幂等：必须建对照表（最容易漏的一条）

迁移会分批、会失败重跑。**没有「源 ID → 目标 atom id」的对照表，重跑就是再迁一遍。**

对照表最少三列：`源 ID | 目标 atom id | 状态`。状态至少三档：已迁 / 跳过（原因）/ 失败（原因）。
它同时是 §5 的验收依据和 §9 的回滚依据。

### 4.5 去重提示怎么判

写入侧遇到相似内容会给一条**提示**（不阻止写入）。它有两种含义，必须人工判一次：

- **同一件事** → 收成一条（后写的标 `supersedes` 指向先写的）；
- **同一主题下的相邻结论** → 两条都留，忽略提示。

把它一律当「重复」删掉，会丢掉本来该有的相邻结论。

**[agent 检查表 4]**

- [ ] 已试迁 5~10 条并召回验证
- [ ] 分批按源库的簇分组，不是按时间序
- [ ] 只迁主库；其余状态有书面理由
- [ ] 对照表三列齐备，状态三档齐备
- [ ] 每条去重提示都判过一次（同一件事 / 相邻结论）

## 5. 验收：四条判据，每一条都要「能红」

| # | 判据 | 怎么测（**要写成能构造失败的形式**） |
|---|---|---|
| 1 | 源库主库条目**每一条**都写过 | 对照表行数 = 源条目数且失败为 0；**再随机抽 3 条源 ID 反查目标 atom** —— 只对计数不算验 |
| 2 | atom 增量**可解释** | 预期 = 源条目数 × 平均切分数。偏差超过两成就去查：切分阈值变了？还是有条目被静默跳过？ |
| 3 | 抽样**能召回** | **抽源库里最冷门的条目**，用它的原话去召回。抽显眼条目一定命中 —— 那是恒真判据 |
| 4 | 源库**未被动过** | 迁移前后各取一次源库统计，必须相同；全程只调读接口 |

**判据 2 为什么重要**：粒度从「卡」变成「句」，条数翻倍是**正常的**。不知道这件事的迁移者会把「变多了」当成错误去修 ——
而正确的反应是「多了多少，能不能用源条目数解释」。

**判据 4 的边界**：迁移是**单向复制**。顺手在源库上「整理一下」的那一刻，这条判据就不成立了，也没法再验。

**[agent 检查表 5]**

- [ ] 对照表行数对得上，失败清单一并交出
- [ ] 随机 3 条源 ID 反查到了目标 atom
- [ ] atom 增量算得出解释（不是「差不多」）
- [ ] 抽样用的是**冷门**条目，且命中了
- [ ] 源库统计前后一致

## 6. 收尾

### 6.1 迁入即生效：两个必须交代的后果

1. **源库里没过审的内容，迁进来就等于自动通过。** 这是 §4.3「只迁主库」的全部理由。
2. **没有「撤一下」这回事。** 见 §9。

### 6.2 冻结源库，或者写清双写期

源库还活着就会**漂移**，而迁移是快照。二选一，不许悬着：

- **冻结**（推荐）：迁完即宣告源库只读或下线，写进迁移记录；
- **双写期**：两边都写，但必须写明**哪边是权威**、双写多久、冲突怎么合。

不选任何一个，等于让两份记忆各自长成一套事实。

**还有一条来自实测的提醒**：如果源库有「自动沉淀」这类机制，它每轮都在长 —— 那么**「把待审的都迁完」是移动靶**。
要么定时点迁（并写明迁的是哪一刻的快照），要么先冻结再迁。

### 6.3 迁完当天就切换写卡模板

迁入的是「一句一原子」，如果之后还按「一张卡一主题」写，库会当场分成两半 —— 而那时没人记得该用哪套。

做法：把新形态写成**一条规范记忆卡放进库里**（它自己也会被召回），迁移记录里写明「从第 N 条 atom 起按新形态」。

### 6.4 落记录（最少四样）

| 记什么 | 为什么 |
|---|---|
| **源库快照**：时间、各状态条目数、导出的来源 | 以后要证明「迁的是哪一刻」 |
| **映射表**：kind 映射 + 兜底类 | 解释「为什么这条归在这类」 |
| **对照表**：源 ID → atom id | 校验、去重、回滚都靠它 |
| **遗留决定**：没迁的状态、没解决的半过时内容 | 不写就等于失忆 |

**[agent 检查表 6]**

- [ ] 源库的处置（冻结/双写）写进记录了
- [ ] 新写卡形态已成一条库内规范卡
- [ ] 四样记录齐备

## 7. 局限（对应 `0.2.0-dev`）

| 局限 | 对迁移者的影响 | 要做的事 |
|---|---|---|
| **LLM 无删除权** | 迁错了不能自愈 | **迁前备份目标库**（这是操作，不是建议） |
| **无淘汰 / 时间衰减** | 旧结论一直在，而且照样会被召回 | 只能靠 `supersedes` 手动退役，且**要定期做** |
| **无自动沉淀** | 库不会自己长 | 迁完 ≠ 以后都会记得；写入必须由 LLM 主动发起 |
| **topic 层可能退化** | 实测单 atom 主题占比超过三分之二 | 主动用 `topic_hint` 聚；**别指望迁完它自动成型** |
| **edge 稀疏** | 关系层基本不工作 | 别指望靠「图路」把内容找回来 |
| **单机单库** | 没有并发写入的实测依据 | 迁移时别开着别的会话大量写 |
| **编码器依赖模型文件** | 首次使用要能拿到模型 | 离线环境先确认已缓存 |
| **常量上限** | 图推断有条数上限（数千量级）；列表分页有硬上限（50） | 超大库分批验，别一次拉全量 |

**这一节要随版本改。** 上面每一条都是「当前实现」的事实，不是永久设计。

## 8. 假象：目标库和源库不一样，会造成的误判

| 看起来像 | 实际是 | 怎么验 |
|---|---|---|
| 写入成功 = 迁好了 | 只说明落了库 | 抽样召回（§5 判据 3） |
| 条数没少 = 没丢知识 | 一句结论会把上下文切断，语义在切点处分离 | 用源库**冷门**条目抽，逐条读 |
| 有 topic = 组织起来了 | 主题可能只装一个 atom | 看主题规模分布 |
| 目录里是空的 = 那条没内容 | 它没有标题行可摘 | `expand` 看全文 |
| 相似度提示 = 重复 | 也可能是同一主题下的相邻结论 | 人工判一次（§4.5） |
| 取回次数高 = 这条重要 | 那只是**谁在查**留下的痕迹 | 别看这个指标 |
| 磁盘上的版本 = 实际生效的版本 | 进程可能还跑着旧的 | 看 `lattice_ping` 的 version |

**另有一条不算假象、但常被误解**：`origin=import` 是**来源标记**，不是质量标记。导入的条目不会因此更不可信，也不会因此更权威。

## 9. 回滚与不可逆

**迁入基本不可逆** —— 模型侧没有删除权（§0 前提 2）。真出问题时，现实路径只有三条：

| 路径 | 代价 |
|---|---|
| 用户在界面上逐条删 | 量大时不可行 |
| 用备份覆盖目标库 | 会连迁移后新写的一起丢 |
| **不撤销，写新条 `supersedes` 覆盖** | 最省，但库里会留下一批「被取代的迁入条」 |

**所以：迁移前先备份目标库。** 备份这件事写在流程里，不要留在记忆里。

**[agent 检查表 9]**

- [ ] 目标库已备份，备份位置写进迁移记录
- [ ] 已确认撤销只有三条路径（界面逐条删 / 备份覆盖 / supersedes 覆盖）
- [ ] 已告知发起人：**迁入不可逆**

## 附录：一次真实迁移的轮廓（已脱敏）

| 项 | 情况 |
|---|---|
| 源库形态 | 卡片式：一张卡一个主题、带分节、正文有长度上限、**有审核层** |
| 源库规模 | 约百条主库；另有少量待审/已删除条目 |
| 迁移后 | atom 数**约翻倍**（按句切分造成）；主题数接近 atom 数（topic 退化） |
| 执行 | 分 4 批，每批数条到数十条；全程只读源库 |
| 踩到的坑 | ① 分类映射的兜底类没定 → 留下一个非法 kind；② 有 atom 无标题 → 目录里不可见；③ 「把待审的都迁完」是移动靶；④ **第一轮判据漏掉了一类「半过时」内容** |

**关于第 ④ 条，要单独说**：迁移后最常见的一类遗留，不是「服务没了」，而是**「方法看着通用、约束已经换了一套」**。
只用「服务还在不在」去筛，一定漏。判据要加上：**照它做会不会错**。
