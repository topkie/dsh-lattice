# 架构

本文说明 dsh-lattice 的记忆模型与数据流。阅读代码前建议先过一遍。

## 一、概念模型

记忆被拆成六种东西，各司其职：

| 概念 | 角色 | 是否真相源 |
|---|---|---|
| **Atom** | 记忆的最小语义单元（一条结论、一个坑、一个步骤或一组参数） | **是**，唯一真相源 |
| **Topic** | 主题节点，由 Atom 向量增量聚类而来 | 否，可全量重算 |
| **Domain** | Topic 的上层聚类，只做导航与配额 | 否，可重算 |
| **Entry** | 检索入口（别名、关键词、从使用中学到的说法） | 部分是（declared / learned） |
| **Edge** | 关联边（邻近、引用、取代…） | 部分是（declared） |
| **View** | 注入时的组装结果，不落库 | — |

核心一句话：**存储单位 ≠ 注入单位**。存储与召回都在 Atom 粒度（细、正交、命中率高），
注入时按 Topic 组装成三段式文本。

## 二、三条设计原理

这三条被刻意分配到**不同的字段**上，因此机制上无法互相污染：

| 原理 | 落在哪 | 解决什么 |
|---|---|---|
| **知识正交** | `atom.text` | 同一份知识只存一份：省上下文，且消除"相似但不一致"的隐性冲突 |
| **入口冗余** | `entry` 表 | 同一个意思有多种说法作入口，换一种问法也找得到 |
| **链接显式** | `edge` 表 | 不同知识之间的关系写出来，不必指望模型自己连上 |

其中**「入口不参与正交判定」**是整个设计成立的支点：正交只依据 Atom 正文的向量与
词面特征，绝不受入口词影响——因此增加入口永远不会污染正交度。

## 三、存储布局

单库单文件 SQLite，WAL 模式。

```
atom          记忆本体（唯一真相源）
  ├─ embedding  float32[512] 的 BLOB，L2 归一化
  ├─ topic_id   主属主题（唯一）
  └─ flags      位标志，写入时按落位结果落库：
                bit0 = 1 待拆分（pending_split 候选）：写入时**按长度**切分即置上，
                      切出来的每一段都带。候选按长度判据给出、**不判断内容** ——
                      601 字只讲一件事的文本同样会被标上，它说的是「切点没读过内容」。
                      召回命中时锚行标「疑似应拆分（切点按长度，未判内容）」并附本次
                      查询词；界面上两个动作，两者都清这一位、都不执行拆分：
                      确认 → 另记 split_queue 的 confirmed，下次召回提示可按内容重写并
                      声明 supersedes；忽略 → 只写一条日志（split.ignored）
                bit1 = 2 歧义（两个候选接近，落位没把握）
                bit2 = 4 未归类（与任何已有主题都不像）
                bit3 = 8 已被取代（设计说明已命名；**未实现**，被取代关系只走 superseded_by 列）
                bit4 = 16 已归档：默认不召回、不进注入三段、列表默认不列；
                      显式检索（lattice_list 给 flags=16、界面勾「显示已归档」）仍可见。
                      归档只改这一位：内容、向量、入口、边都还在，取消归档即恢复可见
                并入已有主题时不置位。**只说明，不参与任何打分**；旧库的行保持 0，不回溯猜
topic         主题，存 sum_vec 与 n_atoms，中心向量查询时现算
domain        topic 的上层聚类，只做导航与配额 —— **未实现，当前恒 NULL**（表在，无写入方）
entry         检索入口：term + bigram 索引列 + 权重 + 来源
atom_topic    主属（权重 1.0）与次属（0.4~0.6）
edge          记忆之间的关系：declared 由模型声明，inferred 由向量近邻重算
atom_pair     atom 两两相似对（重聚类时填；供图扩展与去重查询用）
forgotten     已删除记忆的墓碑（库里**不存正文**，只留指纹与摘要）
build_info       建库元信息（入口抽取规则标识、来源、构建者、构建时间）
recluster_state  整理（重聚类）的三个时刻：计划、开始、完成
split_queue      待拆分候选：切了几段、是否确认过、入队时间
atom_search   检索侧物化表 → atom_fts（trigram）
              entry        → entry_fts（unicode61 + CJK bigram）
```

**另一个库是独立文件，不在这份 layout 里**：降级日志（`<dataDir>/logs/lattice-log.db`，见第六节）。
它可丢、可删，不是真相源 —— 把它放在同一个文件里，会让「清一段时间窗内的旁路数据」变成一次
碰记忆库的写操作，也会让「主库有哪些表」这个问题的答案随旁路数据漂移。
（0.5.0 之前这里还有第二个旁路库：校准样本 `<dataDir>/samples/recall-sample.db`，已随反馈链一起删除，见第八节。）

### 尚未实现的结构项

库里保留着四个「结构在、功能没接」的位置。它们不是计划外的东西 —— 每一个在设计期都有明确用途，只是实现没做到。写在这里是为了让读库的人不必猜「这列为什么一直是空」。

| 位置 | 打算做什么 | 现在是什么值 | 什么条件下才会实现 |
|---|---|---|---|
| `domain` 表与 `topic.domain_id` | 域是主题的上层聚类，只做导航与配额 | `domain` 恒 0 行；`topic.domain_id` 恒 NULL | 主题多到一个视图装不下、需要再分一层时 |
| `topic.mean_fit` 与 `atom.fit` | 成员到主题中心的平均余弦，用来发现「主题内部松散」，据此决定要不要进待分裂队列 | `mean_fit` 有重算、没有读取方；`atom.fit` 只在写入时算一次，重聚类改了归属却不回填，所以在重建过的库上是旧值 | 体检增加「主题松散」这一项时（届时 `fit` 的回填要一起补） |
| `atom_topic` 的次属：`origin` 为 inferred / declared 的行、权重区间 0.4~0.6 | 主属唯一 + 次属多元 —— 一条记忆只存一份，但可以有多条到达路径 | 只有 `origin='primary'` 的行，权重恒 1.0；召回不读次属 | 召回要按主题路径扩展、而不只看向量近邻时 |
| `atom.polarity` | 给判定型的陈述打 -1 / 0 / 1，供注入排序使用 | 工具层没有这个参数，写入恒 NULL；它的用途本身也还没定下来 | 注入排序需要区分陈述与断言时（或届时删列） |

另有两点要单独说明，免得和上面四项混在一起：

- **没有 `meta` 表**：0.5.0 曾把它留给外部标定包写校准快照（包在同一个事务里写 5 个键，写之前要求表已存在）。标定功能退役、标定包归档后，这张表在 0.9.0 的结构里删掉 —— 它当时唯一的读写方已经不在了。若将来要重新标定，先改标定包的存储，再单独加一张表；跨包契约不能由本仓库单方面恢复。
- `edge` 里 `origin='declared'` 的行是**已实现、本库没用过**：写入侧完整（含自指与目标存在判断，`supersedes` 被拒在 `edges` 参数外），只是还没有调用方传过关系。

### 归属主题可以被重算改写

`atom.topic_id` 与 `atom_topic` 的主属行是**聚类算出来的**，不是写下来的事实：整理（重聚类）会把主题表整表重算，再按新主题重写每一条 atom 的归属。所以归属会随库里的内容变化而变 —— 两次整理之间，同一条记忆可能从「包管理」挪到「依赖解析」。

由此有一条边界：**不支持手工调整已写入记忆的归属**。不是没做，是不打算做 —— 手动改 `atom.topic_id` 会在下一次整理时被整表重写覆盖，而库里没有地方记「这一条是人定的、别改」。要让一条记忆归到别的主题，改它的内容更可靠：让它更接近那个主题，下次写入或整理会按内容重新落位。

整理时旧主题到新主题的映射由 `resolveOldToNewTopics` 负责（`src/cluster/rebuild.ts`）。它做的是「把新旧两次聚类里指同一个概念的组对上」，让累计数据（入口、样本）跟着走；它不保留任何一条记忆的人工归属。将来若要支持人工归属，得在真相层加一列（例如 `declared_topic_id`），并让所有读归属的地方合并两个来源 —— 那是一次独立的结构改动。
### 为什么有两层全文索引

SQLite 的 FTS5 `trigram` 分词器按 3 字符滑窗建索引，**对长度 ≤2 的查询返回 0 命中**。
中文技术查询里两字词（代理 / 缓存 / 索引）极其常见，只用一个 trigram 索引会让词面
检索路在短查询上**静默失效**。

因此 entry 层再叠一层 CJK bigram 索引：写入与查询使用同一个切词函数，有共同 bigram
即命中。这是精确匹配的严格超集，索引体积远小于正文层。

## 四、检索路径

四路并行，用 RRF（Reciprocal Rank Fusion）融合：

| 路 | 依据 | 说明 |
|---|---|---|
| 向量 | `atom.embedding` 与查询向量的余弦 | 粗筛能力强，细分能力有限 |
| Entry | `entry_fts`（bigram） | 短查询的主力 |
| 正文 | `atom_fts`（trigram） | 长查询与细节命中 |
| 图 | 一跳边扩展 | 补多跳。边有两类来源：模型**声明**的关系与召回时按余弦现建的近邻（都是 `atom↔atom`）。写入产的 `atom→topic` 边不进图路 —— 它的另一端不是 atom |

融合之后**排序只用余弦**。RRF 分是名次量纲（`w/(RRF_K+i+1)` 逐路累加，`RRF_K = 60`），
top1 恒为 1/61，它只携带「命中了几路、在各路排第几」，不携带相关性语义 —— 拿它判
「这条有多相关」等于拿名次当分数用。所以它只负责**合并通道**，排序与判定都改用余弦。
原先那层「按归属关系加权」（主属 1.0 / 仅次属 0.76 / 仅图路 0.70）已删除：它只改先后
不改集合，而集合指标（目标文档有没有进注入段）对它不敏感，实测四个指标逐位相同。

**判定不看绝对线，看本库的相对分位**（`src/pipeline/refdist.ts`）：一组与库无关的内置
问句（48 条）在本库各查一次，取各自最高余弦的 90 分位作参考线；这条查询的最高余弦
高于它才判「库里有针对这个问题的内容」，否则注入段一个字都不给。用相对分位是因为
绝对线不可标定 —— 三族语料的实测切点差 0.11，且 12–96 档的发布值与复现值方向相反
（详见 `docs/DEVELOPMENT.md`「阈值登记」末节）。

**截断只看字符预算**：按余弦降序逐条装，装到预算为止（默认 5000 字符，单条超过 1200
就截断），装不下的条数写进尾部说明。旧形态按 55/20/25 给三段分配配额，实测预算只用
到 76%（4566 / 4587 / 4531 字符），入口用 74%、路用 28% —— 约 1400 字符既没给锚也没
被别的段用上，所以那套配额取消了。

**装填之前有两道压制**，都会让结果变短，所以两道都在 `view` 的回执里分开报数：

| 压制 | 判据 | 留哪条 |
|---|---|---|
| 重复 | **同一来源**（`source`）且 3-gram 覆盖 ≥ `DUP_TEXT`（0.7） | 余弦高的那条 |
| 取代 | 这条的 `superseded_by` 指向的那条也在结果里 | 只留新条 —— 旧条内容已过期，分再高也不是答案 |

重复压制为什么不按主题分桶：实测同文档的 atom **59%–90% 落在不同主题**，按主题分桶
等于把「同一篇里的重复」漏掉，同时把「不同篇的不同内容」误判成重复。为什么不用余弦
门槛判重复：同文档对的余弦（中位 0.62–0.78）与跨文档对（0.48–0.63）大面积重叠，而
3-gram 覆盖能把「逐字重复」（1.000）与「同文档不同小节」（0.242–0.573）干净分开。
**来源为空的条目一律不参与比较**：没有来源就证明不了同源，而整库一个空桶会让全库互相比
（实测把「系统代理必须走本地端口…」与「系统代理配置本地端口…」判成重复，覆盖度 0.800）。

取代压制的条件是「取代者也在**结果**里」，不是「也在候选里」：取代者只落在候选集里（低分）时把旧条压掉，等于这一组什么都不给。所以压制在截断前做、判据在截断后核，不满足就把旧条放回。被取代的条目在列表、界面搜索、展开里仍然可见，并标「已被 #N 取代」。

**scope 过滤要覆盖到「邻居」这一跳**：四路各自按 `a.scope = ? OR a.scope = 'global'` 过滤，
图路也一样。只过滤种子不过滤邻居时，别的域的 atom 会经一条边进到候选集合里 —— 它和
种子一样参与排序，最后被当成一条正常结果装进注入段，调用方也无从分辨。

**域维度只有一个：`scope`。** 早先的 DDL 里还有一个 `atom.project_key` 列（`forgotten` 也有），
但四路的过滤条件从来没有读过它 —— 写进去的值不改变任何一条路径返回什么。两列语义重复，
0.9 起一并从 DDL 删除，`idx_atom_scope` / `idx_forgotten_scope` 也只含 `scope`。
留着它的代价不是多一列：填了却不影响结果的参数，比没有它更容易让人以为隔离已经生效。

**`topic` 不带 scope，也不打算加。** 主题是聚类结果，它的成员已经是 atom —— 域写在 `atom.scope` 上。让 `topic` 也带一份 scope，就是让派生层存一份真相层的副本：改一条 `atom.scope` 之后两处必有一处没跟上，而「哪一个是对的」没有答案。跨域的 atom 因此可能落进同一个主题（聚类目前是全库一次），这是有意接受的不精确：召回在 atom 上过滤，主题只决定「归到哪」，不会把一个域的记忆带进另一个域的结果里。
### 关系边：声明与推断

`edge` 表里同时住着两类来源不同的边，语义与生命周期都不同：

| origin | 谁产生 | 重建时 | 进图路？ |
|---|---|---|---|
| `declared` | 模型在 `lattice_write` 里用 `edges: [{type, target}]` 显式声明 | **不动** —— 声明一次就是一条事实 | `related` 进 |
| `inferred` | 向量近邻（`near`）与 `atom_pair`（`duplicate`）。全量重建走 `inferEdges`；新写入的一条由 `linkNewAtom` 当场补 | 全量重建先删自己那批再写新的；当场补边不删旧边 | `near` 进 |
| `untyped` | 写入时记的「这条记忆当时最像哪个主题」（`atom → topic`） | 按主题身份一并改写或删除 | 不进（另一端不是 atom） |

`edges` **不收 `supersedes`**（2026-10-21 起）：取代关系用 `lattice_write` 的顶层参数
`supersedes` —— 它才会写 `atom.superseded_by`，并在召回里让旧条让位给新条。走 `edges`
声明取代会被拒，拒因随回执返回。

**图路认哪些 kind**：`GRAPH_KINDS = near / co_occur / refines / requires / related`。
`supersedes` 与 `duplicate` **刻意不在表里** —— 它们服务于「注入时只出一条更高分的」，
不是邻居扩展信号；放进来会让「已被取代」的条目重新进入候选。

**confidence 在两个来源上是两个量**：推断边带相似度（没有相似度时用占位中位数 0.5），
声明边恒为 1.0 —— 声明本身就是证据。它只决定**图路内部**的先后：每个种子先留下哪几条
邻居，多出来的在候选上限处被截掉。它不直接进候选的排序分（`final` 是余弦），但会经
图路的名次间接决定谁进得了候选集合 —— 换掉两条声明边的 confidence，被截断的邻居会变。

**边在注入文本里不再有标记**：0.5.0 起注入段只有【入选】一段，路段的 `[related·声明] …`
与 `[near 0.83] …` 随路段一起取消。声明的边现在只能从 `lattice_expand` 的回执里看到
（见下一段）；这是有意的取舍 —— 注入段的每一行都是一条结果，不是线索。
`lattice_expand` 另把这条记忆**声明出去**的关系逐条列在正文之后（`- related → #12 …`），
推断边不在那里重复列 —— 它们的去处是召回的路段。

**声明的边界**：一次写入最多声明 16 条边（与推断边的出度硬上限同一个常量 `OUT_DEGREE_CAP`）。
两个来源各自计数、不合并：推断边每 atom ≤ 16，声明边每批 ≤ 16，所以同一个 atom 的边可以
多于 16 条 —— 它限的是每个来源的条数，不是总出度。type 不做白名单，只校验长度（≤32 字符）
与字符集（小写字母、数字、下划线，且以字母开头）—— 后者是硬要求：图路按 kind 字面量比对，
写成 `Related` 的边会安静落库、也安静地不进图路。不合法的边**只拒边、不拒记忆**，
拒因随写入回执逐条返回（见 `src/pipeline/write.ts` 的 `validateDeclaredEdges`）。

**声明边不写旁路库**：一次写入只往主库写一个文件，不碰日志库、也不产生任何新库文件
（此前这条专门断言过「不写样本库」，样本库删掉后它变成更强的一句：数据目录里只有一个 `.db`）。声明边与记忆
在**同一个事务**里落库，所以不存在「记忆进去了、关系没进去」的半成品；切分写入时关系只落在
第一条，以免同一批关系在几段上各复制一份。

**重建不覆盖声明**：`inferEdges` 的删除条件是 `origin = 'inferred'`，`declared` 一行不动；
写新边时用 `ON CONFLICT … DO NOTHING` 而不是 `DO UPDATE` —— 声明边若与某条推断边撞同一
（源、目标、kind）唯一键，**声明保持为声明**，不会在重建里被改写成派生物（改写了就会在
下一次重建时被一起删掉）。判据是「全量重建前后，边表的 origin 分布不变」。

**同一条边一旦被声明过，推断的那条从此进不来**：唯一键撞上时 `DO NOTHING`，先落库的
声明行留下、推断行被跳过。这是「声明是真相源」的直接后果，不是缺陷 —— 这条边此后只按
`origin = declared` 解释：重建不删它，也不会把它改写成派生物。


## 五、写入流程

```
提交 Atom
  → 编码（失败则降级为纯词面模式）
  → 定位：与各 Topic 中心算余弦，取 top2；同时算与该 Topic 成员的词面重叠
      ├ 余弦与词面双达标        → 并入最近者
      ├ 余弦中等且明显领先      → 新建 Topic + 邻近边（候选留给图扩展）
      ├ 两个候选接近（差 < 0.06）→ 新建 Topic + 邻近边（设计上要标「歧义」，**当前未实现**）
      └ 全部偏低（< τ_new）     → 新建 Topic，不留边（设计上要落「未归类」，**当前未实现**）
  → 生成入口（声明 / 抽取）
  → 声明边（`edges`：形状在事务外校验，目标存在与自指在事务内判）
  → 单个事务提交，固定行数
  → 提交之后：补推断边（只算这条与全库的 near 边）、刷新主题统计
```

**新写入的记忆立刻有推断边**：提交之后会用这条记忆的向量与全库算一遍余弦，把过线的近邻写成双向的 `near` 边（`linkNewAtom`）。它与全量重建（`inferEdges`）有三处刻意的差别：不重算邻居的出度（入边可能多几条，不会少）、不产生 `duplicate` 边（那要读 `atom_pair`，而 `atom_pair` 本身是重建的产物）、不删任何旧边。用途是让刚写下的东西马上能被图路找到，不是替代全量重建；建边失败不阻断写入，留下的缺口由 `scripts/rebuild-graph.mjs` 补齐（召回不建边，见下文「图路状态的判据」）。
歧义情形**不阻塞写入**：写入方给不出归属时，落库并保留一条指向最近主题的边，
让「该归到哪」变成可以事后修正的问题，而不是让这次记忆写不进去。

**为什么落位要两票**：向量余弦擅长判断"相关 / 不相关"，但在同一大类内部区分度不足。
用真实模型在 8 组同义改写上实测：

| 样本对 | 余弦 min / p50 / max | 词面 Jaccard min / p50 / max |
|---|---|---|
| 同主题（同一件事的不同说法） | 0.811 / 0.897 / 0.956 | 0.059 / 0.229 / 0.471 |
| 跨主题 | 0.375 / 0.509 / 0.633 | 0.000 / 0.000 / 0.061 |

两个量都分离，但**同一个技术域下的不同子话题不在"同主题"这一列**——它们的余弦只有
0.5~0.7，会被分成不同主题。这不是判据失灵，而是"一域一事"的正交要求：想让两条记忆
归到一起，应当显式声明，而不是把阈值调低。

阈值因此取在分布的下界附近（余弦 0.78、词面 0.05）。取底线而非中点，是因为两类错误
代价不对称：**误并是静默的知识损坏，漏并只是多出一个主题**。

## 六、降级

引擎允许降级，但**必须留下痕迹**：

| 失效点 | 行为 |
|---|---|
| 编码模型不可用 | 写入仍成功（向量置零），召回跳过向量路；正交性由词面那一票兜住 |
| 词面路整体失效 | 召回元数据标记，计入健康指标，而不是静默只剩向量路 |
| 短查询在 Entry 层也落空 | 同样标记——这通常意味着索引或切词出了问题 |

降级痕迹同时写入**独立的日志库**（与记忆库分开的 SQLite 文件）。日志只收白名单内的
事件与字段：时间、等级、事件名、数值、错误类名或错误码；查询文本、atom 正文与 id、
文件路径、模型名都不写入。写入只能经 `src/log/` 的入口，且先入内存队列（召回路径上
没有同步 IO）。

等级分三档，入口按等级分三个：`log.info` / `log.warn` / `log.error`，调用点不手写级别
字符串。**级别由事件本身决定**，不由「有哪些档可用」倒推：做成了的事记 `info`（如重标完成），
降级但还能用记 `warn`（词面路失效、图路不可用），本应成功却失败记 `error`（日志自身写不进）。
底层的 `logEvent(level, event, detail)` 仍然是唯一写入口 —— 三个函数只是它的包装，
白名单与字段过滤都在底层，包装层不做任何放行。单文件超过 4 MB 轮换、最多保留 5 个文件。日志不是真相源 —— 可以丢、
可以删：用户在设置页能导出 CSV，也能清空，两者都不碰记忆库。

## 七、体检（只读）

`src/pipeline/audit.ts` 回答「这个库现在长什么样」。数据出口只有一个：只读路由
`/api/lattice-audit`（状态面板消费它；口径只写在这一处，面板只做展示）。

它**不是模型侧的工具**：模型写、查、展开、列表，不需要「体检」；而结构比例只作参考，
工具化会把参考值直接递到模型手里，容易被读成结论。
模型侧固定六个工具：ping / write / recall / expand / list / feedback。

报出的指标：

| 指标 | 读什么 | 回答什么 |
|---|---|---|
| atom / topic 数 | `atom`、`topic.n_atoms > 0` | 库的规模 |
| 单成员 topic 占比 | `topic.n_atoms = 1` | topic 层退化（每条记忆各自成主题） |
| atom / topic 比 | atom 数 ÷ 有成员的 topic 数 | 同上；1.0 即完全退化 |
| 图路状态 | `edge` 按 origin 分组（`src/graph/infer.ts` 的 `edgeOriginCounts`） | 图路有没有输入 —— **两类边都算**：推断边（派生物，重建会整批换掉）与声明边（真相源，重建后仍在）。两类分开报数；体检与召回都只读，不建边 |
| 入口噪声 | `entry` 按 origin 分组 | 每 atom 平均入口数、learned 占比 |
| 高相似未合并对 | `atom_pair`，且两个 atom 分属不同 topic | 几乎逐字重复却占着两个主题 |
| 孤立 atom | 无边且单成员 topic | 既没有关联也不属于任何主题群 |
| 从未被召回 | `atom.recall_hits = 0` | 只进过库、从未被取回 |

**图路状态的判据是两类边之和。** 只有声明边、一条推断边都没建出来的库，图路照样有输入，
所以不能报「没建过」—— 这个形态在 2026-10-19 的审核里被发现两处报得不一样（体检说
`not-built`、召回说 `built`）。现在两处都**只读**：召回报一句话「声明边 N 条，推断边
M 条」，体检报三态（`not-built` / `built` / `too-large`）—— 一个给人看，一个是体检判定，
不共用词表。

**读路径不建边。** 推断边是几何派生物：它的产生条件是「向量变了」，不是「有人查询」。
所以读侧只检测、只提示，不修；重建由写入路径（`linkNewAtom` 给新 atom 局部补边）与显式
命令（`scripts/rebuild-graph.mjs`）负责。这条规则也让只读连接上的召回与可写连接逐字符
一致 —— 诊断与对照实验都走只读。

**「无数据」与「没有发现」分开报**。`atom_pair` 由重聚类建立，空表因此有两种含义：
没建过（先跑一次重建）与建过但没有（比过了，没有）。体检读 `recluster_state` 里的 `completed_at`
区分它们；这个标记由 `rebuildAtomPairs` 在写表后留下。空库报 `dataState: 'empty'`，
比例给 null 而不是 0 —— 0 会被读成结论。

**比例不设红线。** 三个历史值（0.912 / 0.59 / 0.695）随领域混合度变化、互相矛盾，不能
当判据。能判的是行为：`scripts/probe-topic-health.mjs` 在临时库里构造七条分属四个领域的
写入，同领域组内 ≥2 条并入同一 topic 为健康、七条各自成 topic 为失效。它不进体检
（体检只读）、不在用户库上跑、也不进门禁的常规路径。

## 八、反馈（工具定义保留，当前未启用）

模型对召回的反馈**不再是本插件的输入**。判定用的是「48 条与库无关的问句在本库各查一次，
取各自最高余弦的 90 分位」（`src/pipeline/refdist.ts`）—— 那是**分布**问题，不需要标签；
而反馈提供的是标签。链条的另一端（样本库、四道闸、重标、切点扫描）此后依次拆除，
最后一条是这个工具本身。

`lattice_feedback` 的**定义**还留在 `src/tools/index.ts`（`FEEDBACK_TOOL_SPEC`），
但**不进工具表**：模型看不到它，也就不会拿它当可用能力去试。保留定义的用处是把
「这里曾经有什么、为什么没有、什么条件下重启」固定在代码里，而不是只留在 git 历史里。

它曾经写的是独立 SQLite 文件 `<dataDir>/samples/recall-sample.db`，表 `recall_sample` 记
时间、正负、来源、本次召回的 top1、查询向量、命中的 atom id、失效标记、编码模型名，
**不存查询原文**。删它的直接原因：真机样本库只积累到 1 条，四道闸里「正样本 ≥ 10」
那道永远不满足，重标在默认配置下从未发生。重启条件：先说清「哪条阈值会被它改写、
改写依据怎么复算」；只在离线评估（改一版召回比对前后）与人工审计里用标签，不需要这个工具。

两个来源（历史）：

| 来源 | 谁产生 | 写什么 |
|---|---|---|
| `feedback` | 模型显式调用 `lattice_feedback` | 上次召回【入选】段的第几条被判为有用 / 无关 |
| `auto` | 召回时按纯度规则自动收集 | 明显无关或落在不确定带的负样本 |

容量曾由两条规则约束：90 天、总量 1 万条（超出按时间淘汰最旧），「明显无关」那一档另设
2000 条上限；换编码模型时旧样本**标失效但不删** —— 那是换模型前后对照的唯一材料。
这两条是「旁路数据该怎么留」的现成判据，将来接任何带标签的离线材料都可以照用。

**模型引用 id 只发生在「指向历史记忆」时**：`edges` 与 `supersedes` 用 atom id（目标是历史
条目，没有序号可用）；`lattice_feedback` 用 1-based **序号**（目标是「刚才那次召回的第几条」）。
让模型说位置、由插件解析成 id，是「模型管语义、插件管结构」这条边界的直接体现。
这里的「第几条」指 **当次注入的【入选】段**（模型真正看得见的那几行），不是融合后的全部命中：
一次召回的命中通常二十余条，而【入选】段受字符预算约束、常只展示十几条，两者并不相等。
让模型去数它看不见的条目，等于把猜测记成校准样本。

两个判据与工具是否启用无关，是「哪类数据该落哪」的判断：

- **查询↔记忆不能写成 `edge`**：`edge` 是「记忆↔记忆」，不是同一条数据；负样本更造不出语义成立的边。
- **旁路写入不发生在召回路径的同步部分**：入队后在下一轮事件循环批量落盘，所以召回耗时与旁路是否触发无关。

## 九、可重建性

除真相源外的一切都可由 Atom 重算，于是：

- 备份只需覆盖 Atom 与 declared 数据
- 算法升级不需要数据迁移
- 结构变更是一次纯函数计算，可以 diff、可以回退

**但身份必须稳定**：重聚类后要把新簇与旧主题按中心相似度配对并**沿用旧 ID**，
否则所有次属引用与边都会失效。能重算不等于可以随便重算。

## 十、运行时可变状态

进程里只有四处状态会在运行期间被替换。它们构成一张**完整清单**：清单之外的东西
（配置、阈值常量、schema 版本）从启动到结束不变，读取时不需要任何快照。

| 状态 | 形态 | 替换点 | 读取方式 |
|---|---|---|---|
| `current: Runtime` | 模块级单例 | 首次 `getRuntime`；`closeRuntime` 置 null | 工具入口取一次，整段操作用它 |
| 编码器 `extractor` / `state` | 模块级变量 | `resetEncoder`、加载失败 | `ensureEncoder` 之后直接用 |
| 日志模块 `state` | 对象，字段可变 | `configureLog` | 每次写日志现读（无跨 `await`） |
| 样本模块 `state` | 同上一行 | `configureSamples` | 同上 |

**0.5.0 删掉的那一处**：原先还有 `rt.calibration`（重标成功后整体替换的一整套参数）。
它满足「可替换 / 一次操作读多次 / 两次读之间有 `await`」三条判据，所以当时需要快照。
参数整层退役后没有「换代」这回事，快照也随之取消。

**判定用的参考分布不是快照**：它由 `src/pipeline/refdist.ts` 按当前库现算，缓存的键是
atom 行数 —— 库没变就不重算，变了就整份重算。它是一份派生量，不是可替换的参数；
落库会造出第二个会漂的副本（结构版本 5 改造时的教训），所以只在内存里。

**阈值这件事分两层，各有唯一真相源**：模块默认值看代码里的常量（`satisfies ThresholdValue`
就写在常量定义旁边，`src/thresholds.ts` 负责登记与核对）；取值依据看每条登记项的
`finding` 与 `docs/DEVELOPMENT.md` 的「阈值登记」表。
`src/thresholds.ts` 只登记定义位置、可变条件与依据指针，不复制任何一层的值。

**一个不属于这张表的对象**：`rt.db`（连接）。它的**引用**不变，但连接本身会被
`closeRuntime()` 关掉 —— 若某个操作在 `await` 期间遇上关闭，后续用这个连接会抛
`ERR_INVALID_STATE`（`database is not open`），而错误发生在离关闭点很远的地方。
这不是参数换代问题，处置方向也不同（操作期间不卸载，或做 in-flight 计数），所以不并入
上面的读取纪律。

**新增可变状态时**：先加进这张表，再写替换点。不在表里的状态不得中途替换 —— 这条靠类型
（`Readonly<RuntimeConfig>`、常量 `as const`）与代码评审保证。
